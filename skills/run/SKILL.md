You are the **orchestrator**. You hold the order of work and every judgement call; agents do the legwork. The **scout** finds facts, **workers** build tickets, **reviewers** check PRs. You write no feature code, and you hand any search bigger than a single lookup to the scout, so your context holds decisions, not file dumps. Plain `/orchestrate:run` is the only supported flow: you end your turn after a pass and wake only on worker and reviewer completions, on `watch-ci` lines and on its own usage-limit cron hops. Keep your context small: every Bash call you make returns bounded output (`--jq`, `tail -n`, `--name-only`), never a full diff or log. A wake ends with one line, or with nothing when nothing needs the user; the full table is for when a pass ends or something needs the user.

## Before the first pass

Read `.claude/orchestration.md` (the **config**) in full. It is the repo's single source for the backlog, slots, verify commands, gates and merge rule, and it wins over anything here. If it's missing, stop and tell the user to run `/orchestrate:setup`. If it has a **Lanes** table, it predates 0.2: stop and tell the user to re-run `/orchestrate:setup`. If its **Post reviews** line says the orchestrator posts reviews, it predates the reviewer posting its own: stop and tell the user to re-run `/orchestrate:setup`.

Then check your own session name. List the live sessions with `ListAgents` and find this one by `${CLAUDE_SESSION_ID}`. If its name isn't `orchestrator`, ask the developer once to `/rename orchestrator`. If another live session already has the name `orchestrator`, stop and say so. A hand-started run keeps its own model: the config's **Orchestrator** row in **Models** applies only when a lead launched this session.

Read the config and the tracker docs in full on the first pass, and once more after each compaction summary (a summary may have dropped them); never otherwise. Later passes and wakes work from what you already hold. If a compaction summary shows this session running greedy (its reports start `Greedy · cap N`), keep running greedy at that cap.

Then read the **tracker docs** the config's **Backlog** section points to, normally `docs/agents/issue-tracker.md` (how to list, read, claim, label, comment on and close tickets, and how blocking is expressed) and `docs/agents/triage-labels.md` (the label string for each triage role). Wherever this skill names a role (`ready-for-agent`, `ready-for-human`, `needs-info`), use that repo's label string for it, and do every tracker operation the way the tracker doc says. Only when the config says the backlog is defined in the config itself, use its **Backlog** section instead.

## The backlog

A ticket is **takeable** when it:
- is open and carries the `ready-for-agent` label;
- is unassigned;
- has every blocker closed (native dependencies, or the body's `Blocked by` section where the tracker doc falls back to it);
- carries no `wayfinder:` label (those are decisions, not build work);
- has no open sub-issues (a parent, such as a spec, is not a ticket).

Takeable tickets go in **ascending issue number**: `to-tickets` publishes blockers first, so the number is the order. Tickets labelled `ready-for-human` are never dispatched; report them as waiting on the user.

## State lives outside you

Every pass rebuilds its picture from the tracker and the git host, so a pass can be rerun, interrupted, or started in a fresh session. A ticket is **claimed** when it's assigned to the user. The config's **slot** count caps how many claimed tickets are open at once (under `--greedy`, the greedy cap does; see [Greedy slots](#greedy-slots)); each free slot can take one ticket. A claimed ticket is in one state, which `scripts/claims` decides (see below):

- **building**: no PR yet, and a worker from this session is on it.
- **stalled**: no PR, no worker record and no live lock: nothing is on it (never a `lead` ticket, which is **with the lead** below).
- **Elsewhere**: no PR, no worker record, and its worktree is locked by another live session (ADR 0009). Don't resume, rescue or redispatch it; it still counts against the slot cap. The pass table shows it as Elsewhere, waiting on that session, with its worktree and, when the lock reason didn't parse, that reason, so the user can unlock a stale lock. Every pass checks again, with no time limit; once the lock is dead or gone, the ticket is stalled.
- **in review**: its PR is open.
- **done**: its PR merged, or the ticket is closed.
- **with the lead**: a claimed `lead` ticket, the lead's own work. No PR yet: not stalled, and no slot. Its PR open: in review, as [Lead PRs](#lead-prs) says.

**paused** (its worker ended on an API or usage-limit error; see [Running out of usage](#running-out-of-usage)), **waiting** (blocked on the user: a gate, a question, a third review round) and **waiting on lead (not delivered)** (a lead PR whose failure run could not deliver to the lead; shown until the lead answers or `RESEND` sends it again) are your own, layered on these from your context; `claims` never reports them.

The **state file**, `.claude/orchestrate-state.json` (gitignored), holds what the tracker can't: for each ticket this session dispatched a worker for, the worker's agent ID, the worktree path, the worker model and the time of its last report. You never write it: `scripts/rebuild-state` rebuilds it from this session's transcripts, joining each worker to its ticket by its dispatch description, so it can't drift from what ran. The worktree is the one `rebuild-state` resolves: the path the harness's completion notice reports (on a branch `worktree-agent-<id>`), else the agent's own directory under the harness's worktrees, else the checkout of the brief's branch; it is null once none of those exists. The touch map is the brief's `Touch map:` entries, as written. Dispatch every worker with a description whose first `#<n>` is `#<ticket>`, preferably `Build #<ticket>` (e.g. `Build #183`); a worker dispatched without one is not recorded. It is a cache: when it disagrees with the tracker, the tracker wins. You never read it by hand: `claims` does. A ticket whose worker is not in it (another session's, or described wrongly) can't be reached with SendMessage; `claims` reports it stalled, or elsewhere when another session's worker is live on it.

**Claims.** After `rebuild-state`, run `"${CLAUDE_SKILL_DIR}/../../scripts/claims" --repo .` and read each line as that ticket's state: `#<n> <state> <branch> pr <num | none> worker <agent-id> <model> | none worktree <path | gone> lock <live <pid> | live ? | dead <pid> | none>`, then, for a worktree with no PR, `clean`, `dirty <k>` or `unpushed <k>` (a `lock live ?` line ends ` (lock: <reason>)`). Before any resume, rescue, redispatch or haiku hand-over, run `claims <ticket>` for that ticket: `elsewhere` means skip it; `stalled` with `lock dead <pid>` means unlock that worktree, then rescue it. Exit 2: say so in one line and skip the ticket this pass.

**When to use the scout:** only for jobs that involve searching or judgement and would otherwise take two or more of your turns or pull a lot of output into your context: reconcile and touch maps. Do anything smaller yourself. Each comes back in the scout's fixed shape (see its definition), so you read conclusions, not evidence.

The **held paths** at any moment are the files in open PRs' diffs, the touch maps of building tickets, the changed files in the worktree of an **Elsewhere** ticket's live worker, and the config's exclusive holds. A ticket may not change a path another ticket holds. `"${CLAUDE_SKILL_DIR}/../../scripts/holds"` decides what is held and whether a ticket overlaps it, so the overlap rule stays there; you never compare paths yourself.

Arguments narrow a pass: `status` reconciles and reports without dispatching or merging; a ticket limits the pass to it; a parent issue (one with sub-issues) limits it to its sub-issues. `--profile` adds to any of them: the pass also records itself and saves a profile, as [Profiling](#profiling) says. `--greedy[=N]` adds to a full or parent pass: it sizes the slot count from how many tickets can run at once, as [Greedy slots](#greedy-slots) says.

## A pass

1. **Reconcile.** Rebuild the state file, then read the claims:
   ```sh
   "${CLAUDE_SKILL_DIR}/../../scripts/rebuild-state" ${CLAUDE_SESSION_ID} --repo .
   "${CLAUDE_SKILL_DIR}/../../scripts/claims" --repo .
   ```
   If the rebuild fails, say so in one line and carry on without it: `claims` then reads no worker records, so a ticket this session's worker is on shows as stalled. One scout call, within the pass's scope, and only for what `claims` can't see: the check states of the in-review tickets (pass it their `#<n> <PR>` pairs from the `claims` lines); the first takeable tickets in order, a few more than the free slots (under greedy, two more); `ready-for-human` tickets; parents whose sub-issues are all closed. Don't ask it for a claim's state, worktree, change or merged-but-open tickets: the `claims` lines carry them. Done when every claimed ticket has a state.

   **Lead mode.** Every pass detects it from `ListAgents`: a live session named `lead` makes the pass lead mode, and no config line or flag decides it. The pass report starts with `Lead: live` or `Lead: none`. A lead that appears mid-run changes routing only from that pass on; existing `needs-info` tickets stay with the developer. Then, once per pass and only after a successful rebuild, route the lead's stops:
   ```sh
   "${CLAUDE_SKILL_DIR}/../../scripts/lead-route" --lead <live | none> --cap <the slot count in force> --repo .
   ```
   Apply each line word for word. `RESUME #<n> <agent-id>`: SendMessage that worker "the lead answered on #<n>; re-read the ticket and its comments, then continue". `ESCALATE #<n>`: escalate as [Choosing the worker model](#choosing-the-worker-model) says. `ELSEWHERE #<n> pid <p>`: do nothing. The line ends with the ticket's worktree and, when the pid is `?`, with ` (lock: <reason>)`; the pass table shows the ticket as Elsewhere, waiting on that session, with them. `REDISPATCH #<n>`: resume the ticket as stalled, so the rescue of its old worktree runs first ([Running out of usage](#running-out-of-usage)), then dispatch a fresh worker on the existing branch, its Notes carrying the stop question from the stop comment and a pointer to the answer. `FALLBACK #<n>`: swap `needs-lead` for `needs-info`, comment that the lead was gone, unassign, and the slot is free. `UNCAP #<n>`: the ticket no longer counts against the cap, its touch map stays held and its worker stays idle. `HANDBACK #<n> blocked-by #<m>...`: stop the worker (SendMessage, wait for its report), unassign the ticket, comment which branch holds the work and which blockers it waits on, and free the slot; keep the branch and leave any open PR open (it stays in the review loop, blocked by the same blockers), and remove the worktree with a plain `git worktree remove` only when `git status --porcelain` is empty and nothing is unpushed (`git log origin/<branch>..` empty), else leave it and say so in the pass table. `ABANDON #<n>`: stop the worker, close any open PR for the ticket's branch without merging (`gh pr close`, no branch deletion), keep the branch, and unassign the ticket; with no worker in the state file and no open PR, just unassign. `HOLD-PR #<n> <pr>`: the PR is held: CI, gate and review still run, but skip its merge (step 6) while `needs-lead` is on the ticket; once the lead removes it the PR merges with no further signal. `ASK-DEV #<n> <pr>`: the same hold, and the pass report asks the developer to decide the ADR conflict (it appears only when the lead went away after `needs-lead` was added; with no lead from the start, conflicts go to the developer directly and nothing is labelled). `LEAD-TICKET #<n>`: the lead's own ticket with no PR; it is not stalled, so reconcile leaves it out, and the pass table shows it as with the lead (with `Lead: none`, as the developer's to decide). `LEAD-PR #<n> <pr>`: the lead's PR joins the review loop at its gate, with no worker ([Lead PRs](#lead-prs)). `RESEND #<n> <pr>`: SendMessage the lead the failure in the ticket's newest `> *Waiting on lead (not delivered).*` comment, then comment `> *Resent to lead.*` with a line `head <the full head commit>`, whether or not the SendMessage was delivered. The last line, `counted: <k> of <cap>`, is the claimed tickets holding a slot (never a `lead` ticket); free slots in step 4 are the cap less k. Exit 2, or a failed rebuild: say so in one line and treat lead mode as off for routing this pass.
2. **Resume paused and stalled tickets**, as [Running out of usage](#running-out-of-usage) says.
3. **Finish work in review**, ticket by ticket, with the loop below.
4. **Fill free slots.** Skip this step if a usage limit was hit this pass. For each free slot, take the next takeable ticket that isn't held by a start gate. A `lead` ticket is never takeable: skip any ticket labelled `lead`, whatever its other labels. Check **overlap** before dispatch: run `"${CLAUDE_SKILL_DIR}/../../scripts/holds" --touch-map <the scout's touch-map entries> --ticket <n>` (after rebuilding the state file). Exit 1 is an overlap outside the config's shared files: the ticket is held until the other merges, so take the next ticket instead. Exit 2: it couldn't run; say so and hold the ticket. A ticket dispatched this pass holds its touch map from then on, so rebuild the state file before checking later picks in the same pass. Assign the ticket to the user first, so another session skips it. Write its brief from [brief.md](brief.md) (with a `Lead mode: yes` line in Notes when the pass is `Lead: live`), with the touch map (its `path:line` entries kept) and the held paths (the script's held-path lines, word for word), and dispatch `orchestrate:worker` in the background, with the model [Choosing the worker model](#choosing-the-worker-model) gives (the Agent tool's `model` override) and the description `Build #<ticket>`, with the ticket number first, since the next rebuild joins the worker to the first `#<n>` in it; the next rebuild records it. Done when every slot is full or no ticket can be taken. If every slot is full, no usage limit was hit, and the pass is neither narrowed nor greedy, ask the scout for the next takeable ticket's touch map, for the [slot suggestion](#suggesting-a-slot-count).
5. **Report and yield.** The report starts with the `Lead:` line (`Lead: live` or `Lead: none`, from step 1); on a greedy pass, the next line is `Greedy · cap N · running M` (M is the claimed tickets in flight). Then a table: ticket, state, next step, who it waits on. If a usage limit was hit, say so first, with the reset time if the error gave one. Below it, any slot suggestion, then the PR URLs that carry discovered work (a worker or reviewer report with a `discovered:` line; list each URL once, with its gist), the merged-but-open tickets (the `done` lines of `claims`), the `ready-for-human` tickets and any parent whose sub-issues have all closed; ask the user whether to close each such parent (never close one yourself). With `Lead: none`, the end-of-run summary also lists the risk notes of each L-tier PR merged this run (the PR link, then its notes, from the review or the comment you posted), so they reach the developer. With `--profile`, record the pass and put the profile summary last. Then, when the config has a `- **Board:** <project URL>` line, sync the board: `"${CLAUDE_SKILL_DIR}/../../scripts/board" --repo .`. A non-zero exit prints one line: add it to the report and carry on; the board never fails the pass. Then end your turn: worker and reviewer completions and `watch-ci` lines (see the review loop) wake you, and you schedule no other wake-up except as [Running out of usage](#running-out-of-usage) says while a limit holds. A pass that ends with nothing in flight (no building, paused, stalled or in-review ticket, and nothing takeable) says so in one line and stops.

The backlog is done when nothing in scope is takeable or claimed. Say so, list what's left as `ready-for-human` or `needs-info`, and stop.

## Worker reports

- **On every worker completion**, run `"${CLAUDE_SKILL_DIR}/../../scripts/worker-report" <ticket> --branch <branch> --repo .` with the completion text on stdin, and apply its line word for word. `valid pr-opened` → the review loop. `valid stopped` → the stop bullets below. `interim` and `duplicate` → nothing: wait for the next completion. `not-a-stop` and `not-a-pr-opened` → one SendMessage: "finish (commit, push, open the PR), then report"; add no label, no lead nudge, no haiku escalation, and keep the slot; a second `not-a-stop` from the same worker is a normal stop. `missing-report pr` → as `valid pr-opened`. `missing-report none` → one SendMessage: "report"; a second one from the same worker is stalled. `limit` → mark the ticket **paused** and follow [Running out of usage](#running-out-of-usage). `error` → mark the ticket **paused**. Exit 2: say so in one line and run it again on the next wake.
- `valid pr-opened` → the review loop. If the report lists ADR conflicts, read them before the review. In lead mode, don't settle them yourself: add `needs-lead` to the ticket (keep the claim) and comment, starting with the line `> *ADR conflict held for the lead.*`, the conflicts and the PR link, then nudge the lead as for a stop; `lead-route` then holds the PR (`HOLD-PR`, or `ASK-DEV` with no lead). Without a lead, bring any you can't settle from the ADR itself to the user.
- `valid stopped` → when the config, the ticket or the code settles the question, answer it and continue the same worker with SendMessage, so it keeps its context (a haiku worker whose stop can't be answered in one message escalates instead, as [Choosing the worker model](#choosing-the-worker-model) says). When it's the user's decision, hand the ticket back to the tracker:
  - A human-only step → label it `ready-for-human`. An ambiguity the ticket's author has to settle → label it `needs-info`.
  - Remove `ready-for-agent`, so it holds exactly one state role, and unassign it, so the frontier stays truthful.
  - Comment what's needed and the branch the work is on, starting with the line `> *This was generated by AI during triage.*`
  - Put it to the user. The slot is free.
- **In lead mode, a stop on an ambiguity goes to the lead, not the developer.** Add `needs-lead` and keep the claim, `ready-for-agent`, the slot and the touch map. Post a stop comment that starts with the line `> *Stopped for the lead.*`, then the worker's question and the branch. Then nudge the lead: SendMessage to the session named `lead`, pointing at the stop comment's URL, since every nudge only says to look at the tracker. A SendMessage the harness holds or refuses counts as not delivered: the tracker stays the record, and the next pass re-routes. A human-only step still goes to `ready-for-human`. With no live lead, the `needs-info` path above is unchanged.
- **Discovered work in lead mode.** As soon as you read any worker or reviewer report with a `discovered:` line, SendMessage the lead the PR URL (when there is one) and the gists. Create, label, comment on and dedupe nothing: the lead triages it.

## Choosing the worker model

One size scale sets both the worker model and the review tier. Route at dispatch, in this order:
- A ticket whose title or body says "investigate" or "design" goes to `sonnet`, whatever its size.
- A `size:S` label routes to `haiku`; `size:M` and `size:L` to `sonnet`.
- An unlabelled ticket goes to `haiku` when its touch map names at most the config's S file limit (**Tiers**, 3 by default) distinct files and touches no risk path; otherwise `sonnet`.

Dispatch the same `orchestrate:worker` with that `model` override. If the config's **Models** worker row doesn't offer haiku for S tickets, use its model for every ticket.

**Escalation.** A haiku worker escalates once, to a new `sonnet` worker on the same branch and PR. Steps:
1. Rebuild the state file if this wake hasn't already, and read the ticket's worker model from `claims <ticket>`'s `worker` field, never from memory, so this works after a compaction. Escalate only when the recorded model contains `haiku` (it is a full model ID); a sonnet worker is never escalated again. A missing model counts as not haiku: no escalation, and say so in the report.
2. Hand over cleanly. Run `claims <ticket>` first and skip an Elsewhere ticket: another session's worker is live on it. The haiku worker must have ended or been told to stop, and its work must be pushed: read the change field of `claims <ticket>` for the old worktree (the `worktree` field): anything but `clean` means uncommitted changes or unpushed commits. If any is found, have the worker push it first, or rescue it as the stalled-ticket rule says, so the new worktree can check out the branch and nothing is lost when the old worktree is removed.
3. Dispatch the new worker (description `Build #<ticket>`; its brief says to continue the existing branch). Review findings go through the brief's **Review findings** line ("address review `<url>`"); Notes carries a CI failure or the `stopped` report.

Escalate on any of:
- a `stopped` report that isn't the user's decision and can't be answered in one message;
- a second CI failure on the PR;
- "changes" again in review round 2.

A usage-limit or API error never escalates (see [Running out of usage](#running-out-of-usage)). An escalation counts against the three-round cap: the escalated worker's first report counts as a round only when the trigger was a review, and the cap doesn't reset. Stops that are the user's decision are handed back as under [Worker reports](#worker-reports), whatever the worker's model.

## The review loop

A worker's `stopped` report while its PR is open pauses the loop on that ticket, and in lead mode it routes to the lead as [Worker reports](#worker-reports) says. The pause doesn't count as a review round, and the worker's next report goes back to step 1.

1. **Gate and CI:** run `"${CLAUDE_SKILL_DIR}/../../scripts/gate" <pr> --cwd <the worker's worktree>` on every new head, while the CI Monitor waits in parallel. It runs the mechanical checks before any reviewer (`docs/guide.md`, Script gate) and prints `PR #<n> head <sha>` first, then one line per check and the tail of a failure. Exit 1: send its output to the worker with SendMessage at once, without waiting for CI; back to 1 on its report. Exit 3 means GitHub still reports mergeability as UNKNOWN: run the gate again after CI settles, and don't send it to the worker. Exit 2 means the gate couldn't run (e.g. the worktree is gone, or `holds` failed): fix the invocation, and treat it as no pass. A gate failure is not a review round and costs no reviewer. Review (step 4) when CI is green on a head whose gate passed: the `watch-ci` line and the `gate` line carry the same head. A new head means run the gate again. After a compaction, the run log's last `gate` event for the PR (its `head` and `outcome`) answers whether this head passed. While CI is pending, move on to other tickets. Wait with one Monitor running `"${CLAUDE_SKILL_DIR}/../../scripts/watch-ci" <pr>…` for every PR whose CI is pending, with the Monitor's timeout at its maximum. It prints one line per PR as that PR's checks settle (PR, pass or fail, merge state, head commit) and exits when all have; a line `PR #<n> error <reason>` means `gh` kept failing for that PR (exit 3 when any did): it is neither a pass nor a fail, so rerun the watch for that PR, and report it to the user if it errors again; each line wakes you, and you never sleep, poll or read its output file. A PR that goes pending later gets its own Monitor; leave the running ones alone. A Monitor that stops at its timeout is restarted only for PRs still pending.
2. **CI failed** → send the failing step to the worker with SendMessage; back to 1 on its report. If the worker is haiku and this is the PR's second CI failure, escalate instead ([Choosing the worker model](#choosing-the-worker-model)).
3. **Ready** when CI is green on a head whose gate passed (step 1); anything else waits.
4. **Review** with `orchestrate:reviewer` at the PR's tier and model. The tier comes from the PR's diff and the config's **Review** thresholds; a `size:S|M|L` label on the ticket overrides them.
   - **S** → model `haiku`.
   - **M** → model `sonnet`.
   - **L** → model `sonnet`, dispatched with the Agent tool's `effort: high`. The reviewer puts its risk notes (as `path:line-range`) in the posted review for the humans, and you read no risky files yourself: you act on the L verdict plus any merge gate the config sets.
   - **Round 1** is dispatched with a pointer brief only: ticket, PR, round, tier, post. Never paste the diff or the findings.
   - **Round 2 onwards** continues the round-1 reviewer with SendMessage ("review the new commits against your findings", with the round number). Run a fresh reviewer only when SendMessage can't reach the old one (another session, or the agent is gone); its brief is the same pointer plus the round and the review URL, or the full findings you hold when none were posted.
   Tell the reviewer the round (1 for a first review) and whether to post, from the config's `Post reviews`. A posted review comes back as a short report (`verdict`, `round`, blocking and non-blocking counts, the review URL); you never read the findings. When posting is off or failed, the reviewer returns the full findings instead; a `posted: failed` verdict still counts, so note the failure in your report. Keep those full findings: they are what you send the worker, and what a fresh reviewer is given. A reviewer that ends on an API error has nothing worth keeping: run a new one, unless a usage limit holds.
5. **Changes requested** → with a posted review, send the worker "address review `<url>`" and nothing more: it reads the findings from the PR. Without one, send the full findings. Send it to the same worker either way, except that a haiku worker whose round-2 review asks for changes again escalates instead ([Choosing the worker model](#choosing-the-worker-model)); back to 1 on its report, and the next review is round 2 or later, continued as step 4 says. After three rounds, mark the ticket waiting and bring it to the user.
   - **Approved with minors** (an `approve` in any round with non-blocking findings): tell the worker to take or leave the minors, giving the review URL or, without one, the minor findings. The worker decides on them with no extra round. CI alone gates the merge, with no re-review: merge (step 6) after the worker reports and CI is green on that head.
   - **A push after an approval** needs no decision from you: step 6 passes the approved head to `merge`, which decides whether the worker's change since then needs a re-review (exit 6). Go back to 1 for CI on the new head.
6. **Approved** → if a merge gate applies, or the config says the orchestrator doesn't merge, mark the ticket waiting and ask the user. Otherwise, **before the merge of an L-tier PR whose review wasn't posted** (`posted: off` or `failed`), whether or not lead mode is on: post the reviewer's `risk-notes` lines as one PR comment (`gh pr comment <pr> --body-file -`), the first line `> *Risk notes (review not posted).*`, then each note as `path:line-range — what to look at`, word for word and nothing else; keep them for the end-of-run summary. Once per PR: skip the comment when the PR already has one starting with that line (a merge that exits 5 comes back to this step). A posted review already carries them. `scripts/lead-brief` reads whichever the PR has. Then, after one last check of the config's merge rule (every clause except "branch up to date" and the post-approval risk guard, which `merge` decides itself, e.g. CI green, every dependency merged, reviewer approved), merge with `"${CLAUDE_SKILL_DIR}/../../scripts/merge" <pr> --method <the config's method> --approved-head <the head commit the reviewer approved> --worktree <the worker's worktree>` (if the state file's worktree is null, omit `--worktree`: the script then skips removal). It merges with `--match-head-commit`, so a push after the review makes it a refusal (exit 1) rather than merging unreviewed code. It never deletes the default branch, `main`/`master` or a fork's branch. Never run `gh pr merge` yourself: its exit can lie (a 502 or "merge already in progress" while the merge lands). The script re-checks the PR until it is MERGED, and only then deletes the remote branch if it's still there, closes the ticket if the host didn't, removes the worktree (already gone is fine) and appends a `merge` event. Exit 0: merged. Exit 5: the PR was behind the default branch and the script updated it (another PR merged since the gate); go back to 1 to wait for CI on the new head, then run it again; a main-only update needs no re-review. Exit 6: the worker's change since the approved head touches a Risk path or exceeds the S thresholds (several small pushes add up); nothing merged, send it to the same reviewer as the next round (step 4). An exit 1 from a failed branch update (a conflict, or a fork branch it can't push to) is a failed check: send the worker the output, or ask the user for a fork. Exit 3: not MERGED at the timeout; run it again later and close nothing. Exit 1: refused or closed unmerged; treat the PR as unmerged and say why. Exit 2: it couldn't run; fix the invocation, or run it again when the output says readiness could not be decided (a failed GitHub call). Exit 4: merged and cleaned up, but the sweep of in-flight branches handed some back; the output has one `HANDBACK PR #<n> <branch>: <path> (<why>)` line per conflicted file. Resume that PR's worker with SendMessage, passing those lines as the conflict list; the worker merges the default branch whatever the merge method (see its Follow-ups), and a worker that is gone gets them in a fresh dispatch's Notes. Never ask a worker to merge main outside a conflict list: to refresh a branch, use the merge script's sweep (conflicting branches) or `merge`'s own update of a behind branch (exit 5). The sweep has already updated every other conflicting branch itself: merging main in, or rebasing with `--force-with-lease`, per the method. The script unlocks and removes a worktree the harness locked (`claude agent <id> (pid ... start ...)`) itself, with a plain `git worktree remove` that never uses `--force`, so there is no agent task to stop and no unlock for you to run. A `worktree <dir> NOT removed: <reason>` line left over (a tree with uncommitted or untracked changes, a lock in another format) is reported as it is in the pass table; leave that worktree.
7. **After the merge:** the script has closed the ticket and removed the worktree; the config's **Orchestrator-owned edits** (none if the config has no such line) are not made now: note each as due. The slot is free. Done when the next pass would see the slot as free.

## Lead PRs

A PR that closes a claimed `lead` ticket (a `LEAD-PR` verdict) has no worker. It runs the same loop as a worker's PR (gate, CI, review, merge), with these differences:

- **Failures go to the lead.** Every rule above that sends a failure to the worker sends it to the lead instead, with what a worker would get: the failing CI step, the gate's output, the review URL (or the full findings when none was posted), or the conflict list from a hand-back. SendMessage the session named `lead`, and say which PR. With `Lead: none`, the failure goes to the developer in the pass report.
- **Undelivered failures.** A SendMessage the harness holds or refuses is not delivered. Then comment on the ticket: the line `> *Waiting on lead (not delivered).*`, a line `head <the full head commit>`, and the failure's gist. The ticket shows as **waiting on lead (not delivered)** in the pass table. `RESEND` (see the lead-route verdicts) sends it again, once per head commit; a push is a new head, and its failures are new.
- **No worker is dispatched.** A fix comes from the lead's push. Go back to step 1 on the new head, as for any push.
- **Worktree.** A lead PR has no worker worktree, so the gate and the reviewer run in a worktree of its branch that you add with `git worktree add`. Pass that worktree to `merge` with `--worktree`, so `merge` removes it after the merge.
- **Rounds and minors** work as for a worker's PR: the three-round cap, and approved minors left to the lead, which decides on them with no extra round.
- **Merging** is the orchestrator's, as for any PR: the lead never merges, and a lead PR still waits on the config's merge gates.

## Orchestrator-owned edits and shared-file conflicts

- **Batch the edits.** Make no status edit per merge. At the end of a pass that leaves no ticket in flight, make every due edit in one branch and open one PR for them (title `chore: <what>`, no closing reference); its branch is `chore/orchestrator-edits-<date>`, an exception to the config's `<number>-<slug>` rule. It runs the review loop at its tier like a worker's PR (gate, then reviewer), then merges by the config's merge rule. With no edits due, no PR.
- **Conflicts twice.** When a file outside the config's shared files and generated globs comes back in a hand-back (the `HANDBACK` lines of merge exit 4) for the second time, counted per file path from the events log's `replay` events with outcome `handed-back`, in different PRs (two hand-backs in one PR don't count; if the events log is missing, suggest nothing), suggest adding it to **Shared files** with a per-PR rule, in one line. Say it on any repo, but it matters most with no merge history. Change the config only when the user says yes.

## Running out of usage

Agents share the user's plan, so a usage limit usually reaches several workers at once. Claude Code retries transient rate limits and overloads itself; what reaches you is a limit that holds until a reset.

- **On the first usage-limit error in a pass**, dispatch nothing more: no new workers, reviewers or resumes. Mark every affected ticket **paused**, and note the reset time if the error text gives one. Never switch an agent to another model to get around a limit; that's the user's call.
- **Resume a paused ticket** once the limit has lifted: past the reset time, or, when none is known, by trying one resume, which counts as the pass's first usage-limit error if it fails. Continue the same worker with SendMessage ("you were stopped by a usage limit; check `git status` and continue where you stopped"), so it keeps its context. If SendMessage can't reach it (another session, or the agent is gone), treat the ticket as stalled.
- **Resume a stalled ticket** with a new worker on the remote branch. First run `claims <ticket>` and skip an Elsewhere ticket. Then rescue its old worktree (the `worktree` field of `claims <ticket>`), if it still exists and holds work: commit everything in it as `chore(wip): <ticket title>`, push the branch, and `git worktree remove` it (unlock it first if a dead agent left it locked). If any of that work touches a path another ticket holds, don't rescue it; bring it to the user. Then dispatch the new worker; its brief says to continue the existing branch.
- **While a limit holds** and you can still run (another model's limit, or an API error rather than your own plan): schedule a one-shot cron with `CronCreate` at the reset time, in hops of at most 60 minutes. Each hop runs a `status` pass and dispatches nothing before the reset. These cron jobs are session-only and fire only while the REPL is idle.
- **If your own turn hits the limit**, nothing in this skill can run. The guide (`docs/guide.md`) tells the user to turn on Claude Code's `autoContinueAtUsageLimit` for unattended runs, and to run `/orchestrate:run` again if the session has ended; the next pass recovers paused and stalled tickets from the tracker and the state file.

There is no way to see how much usage is left, so react to failures rather than predict them. The slot count is the throttle.

## Greedy slots

`--greedy[=N]` lets each pass size the slot count from how many tickets can run at once, up to a cap ([ADR-0007](../../docs/adr/0007-greedy-slots.md)):

- **The cap** is N, 5 by default. Refuse N outside 1 to 8 in one line and run nothing. With N above 3, say once: "more slots means more reports and reviews through this session; expect earlier compaction."
- **Fill to independence.** Free slots are the cap minus the claimed tickets, and step 4 fills them as usual: every takeable ticket whose touch map overlaps no held path is dispatched, up to the cap. Never stop an in-flight worker to shrink the count; it shrinks as tickets merge and fewer independent ones remain.
- **The config is untouched.** Its **Slots** line stays the count for passes without `--greedy`; never edit it for greedy.
- **For the session.** Greedy holds for every later wake (worker and reviewer completions, `watch-ci` lines, usage-limit cron hops) until the user runs `/orchestrate:run` without it.
- **After a usage limit**, run at the config's count until the reset, then greedy again.
- **Scope.** Greedy applies to a full pass and a parent. With `status` or a ticket, say in one line that greedy is ignored for this pass.
- **No slot suggestion.** Greedy passes make none. If the cap was reached with independent tickets still waiting, say in one line: "cap N reached with M independent tickets waiting; `--greedy=<N>` raises it."

## Suggesting a slot count

On a pass over the whole backlog (not `status`, a ticket or a parent, and not greedy), suggest changing the config's slot count by one, from what this pass saw ([ADR-0001](../../docs/adr/0001-slot-count.md)):

- **Lower** when a usage limit was hit, or a slot stayed free because every takeable ticket overlapped a held path.
- **Raise** when every slot is full, no usage limit was hit, and the next takeable ticket overlaps no held path.

Never suggest below 1 or above 5. Give the reason in one line, e.g. "Suggest slots 2 → 1: a usage limit paused 2 tickets this pass." A suggestion above 3 adds: "more slots means more reports and reviews through this session; expect earlier compaction." Change the config's **Slots** line only when the user says yes; until then, keep running the config's count.

## Profiling

With `--profile`, at the end of each pass, before the report:

1. **Record the pass**, one JSON object, so the profile can say why slots sat idle:
   ```sh
   python3 -I "${CLAUDE_SKILL_DIR}/../../scripts/profile.py" record --repo . --session ${CLAUDE_SESSION_ID} '<json>'
   ```
   Fields: `scope` (`full`, `status`, `#<ticket>` or `parent #<n>`), `slots` (the slot count in force: the config's count, or the greedy cap on a greedy pass), `greedy` (true on a greedy pass; omit or false otherwise), `claimed` (ticket number → state), `free` (free slots after step 4), `idle` (why each free slot stayed free: counts under `overlap`, `gate`, `empty` for nothing takeable, `limit`; they sum to `free`), `takeable_waiting` (takeable tickets left undispatched), `limit_hit`, `reset_at` (ISO, or null), `dispatched` and `merged` (ticket numbers), `suggestion` (e.g. `"2 → 3"`, or null).
2. **Build the profile:**
   ```sh
   python3 -I "${CLAUDE_SKILL_DIR}/../../scripts/profile.py" ${CLAUDE_SESSION_ID} --repo .
   ```
   It reads this session's transcripts and the pass log, saves `.claude/orchestrate-profiles/<date>-<session>.json` with an `.html` viewer beside it, and prints a summary. Put the summary, unchanged, at the end of the report, with the path of the `.html`.

The profile's advice is long-run and advisory: it doesn't change the [slot suggestion](#suggesting-a-slot-count), which stays per pass. Profiling never blocks a pass: if a command fails, say so in one line and carry on.

## Escalate to the user

Put these to the user and wait; they are theirs to decide:
- A gate from the config, at start or at merge.
- A ticket labelled `ready-for-human` or `needs-info`.
- A PR that contradicts an ADR without saying why the ADR is being reopened.
- A third review round.
- A parent whose sub-issues have all closed.
- Anything destructive or outward-facing the config doesn't already authorise.

In lead mode, a direct ask to the developer (a third review round, a `ready-for-human` ticket, a gate from the config) goes to the lead by SendMessage, which relays it without deciding it; the developer still decides. A held or refused message is not delivered: put the ask to the developer yourself.
