You write the repo's **config**, `.claude/orchestration.md`, which `/orchestrate:run` and its agents read as their single source of rules. The facts come from the repo; the decisions come from the user.

## Steps

1. **Gather facts.** Send `orchestrate:scout` these questions in parallel calls:
   - The tracker docs from `/setup-matt-pocock-skills`: whether `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md` and `docs/agents/domain.md` exist, the tracker each names (a doc naming GitLab, local or any other non-GitHub host stops setup with one line pointing at `docs/adr/0010-github-is-the-tracker-the-scripts-read.md`, since the scripts read only GitHub), and whether every label string in `triage-labels.md` (including `needs-lead` and `lead`) exists on the tracker. Only if the docs are missing: which host, how tickets block each other, how a ticket gets claimed, and where an ordered backlog lives or could live.
   - The build, test, lint and codegen commands (Makefile, package scripts, CI workflows), and which CI checks gate merges.
   - The top-level layout by directory and ownership: candidate exclusive holds, and the paths where a wrong change is costly (candidate risk paths).
   - Conventions in the instruction files (`CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING`): commit and PR format, docs every change must update, files many changes touch.
   - The default branch and the merge methods the host allows.
   - Anything that collides across parallel worktrees (fixed ports, one shared local database, container names), and the gitignored files the tests need.
   Done when each question has an answer or a `not found`.
   Then **infer the shared-file rules** before asking anything. Sources, in order: the docs (`CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING`, CI workflows, the Makefile, `.gitattributes`) and the history. For history run `gh pr list --state merged --limit 50 --json number,files`, and propose every file changed by at least 25% of the PRs fetched. With fewer than 10 PRs, treat it as no history and use the docs alone. Take from the docs the per-PR rule for each shared file (e.g. a changelog line), the regenerate command for each generated glob (Makefile or CI codegen steps, `.gitattributes` `linguist-generated` or `merge=` entries), and any status edit the repo says only the orchestrator makes (orchestrator-owned edits; none unless the repo's rules require one). With no `gh`, no auth or no merge history, say so, use the docs alone, and put the shared files to the user as an open question. Ask only for what neither source answers.
2. **Draft** the config from [config-template.md](config-template.md): facts filled in, and a recommended answer written beside each decision.
3. **Decide with the user.** Put every open decision in one round, numbered, each with your recommendation: the backlog source (the tracker docs; if they're missing, recommend running `/setup-matt-pocock-skills` first, and otherwise settle the backlog and its order in the config; if labels are missing, recommend creating them, `needs-lead` and `lead` included), the slot count (recommend 2; 1 when a parallel-worktree collision has no fix; 3 only after asking about the user's plan, never more; `/orchestrate:run` suggests changes from real passes) and any exclusive holds, the gates, whether the orchestrator merges, the models (recommend haiku workers for S tickets, written with the file limit from the **Tiers** line), the review tiers and their thresholds, the risk paths, whether reviewers post their reviews on the PR (recommend yes), the shared-file rules, and the fix for each parallel-worktree collision. Done when the user has answered each one.
   Two checks, advice only, before the user answers. **Risk-path share:** take the files of the same recent merged PRs; if more than half would be L under the proposed risk paths and thresholds, advise listing only the paths where a wrong change is costly to undo, and using merge gates where a human must look; say it gets no weight when there is no history (fewer than 10 merged PRs counts as none). **`autoCompactWindow`:** read it from the first file that sets it, in the order `.claude/settings.local.json`, `.claude/settings.json`, `~/.claude/settings.json`. If it is above 200000, print one line: "autoCompactWindow is <n>; 150K to 200K keeps the orchestrator's and the lead session's context bounded (set it in your settings, or start the session with `--autocompact 150000`)." If it is unset or under 200000, say nothing. If none of the files can be read, say the setting couldn't be found and move on. **Setup only reads these settings and prints advice; it never edits user config.**
4. **Write** `.claude/orchestration.md`, plus a `.worktreeinclude` that lists the patterns of the gitignored files workers need (patterns only, never file contents). Suggest `.claude/worktrees/`, `.claude/orchestrate-state.json` and `.claude/orchestrate-profiles/` for `.gitignore` if they're missing. Leave committing to the repo's normal flow, and tell the user which files to commit. If no skill whose name ends in `:pr` is listed, tell the user worker PR bodies will be plain; setup does not fail.
5. **Offer the board**, an opt-in GitHub Projects board that `/orchestrate:run` syncs every pass so you can see work in flight (it works with or without a lead). Ask once; on a no, or when `gh` is missing or unauthenticated, say so in one line and skip. On a yes, run `gh project list --owner @me --limit 1`: if it fails because the token lacks the `project` scope, give the user `! gh auth refresh -s project` to run themselves, and offer retry or skip (never run it yourself). Then create the project: `gh project create --owner <repo owner> --title "<repo name> orchestrate" --format json` and link it with `gh project link <number> --owner <repo owner> --repo <owner>/<repo>`. If the owner is an organisation and that fails, fall back to `gh project create --owner @me ...`, which is the developer's own account and stays unlinked, and say so. If both fail, skip with one line. On success, write the line `- **Board:** <project URL>` (the `url` from the create output) under `## Backlog` in `.claude/orchestration.md` yourself: no hand edit. The `Stage` field and the cards are made by `scripts/board` on its first sync.
6. **Offer SSH under the sandbox**, only when `origin` is an SSH URL (`git@…` or `ssh://`). On macOS, `git fetch`, `pull` and `push` over SSH fail inside the sandbox even for an allowed host, because plain ssh ignores the sandbox proxy ([sandboxing docs](https://code.claude.com/docs/en/sandboxing)); agents then see `Permission denied (publickey)`. A plugin can't ship sandbox settings, so ask whether to add `git fetch *`, `git pull *` and `git push *` to `sandbox.excludedCommands` and the remote's host to `sandbox.network.allowedDomains`. Say plainly that **those three git commands then run unsandboxed** and can reach any host. On a yes, run `"${CLAUDE_SKILL_DIR}/../../scripts/sandbox-git" --repo .`: it merges into `.claude/settings.local.json` (never the checked-in `settings.json`, never `~/.claude`), keeps other keys, adds that path to `.gitignore` if it isn't covered, refuses a file that isn't valid JSON, and does nothing for a non-SSH remote. Tell the user to leave `settings.local.json` uncommitted. On a no, nothing is written: workers fall back to HTTPS through `gh` (see `agents/worker.md`).
