# How does a stop end on the tracker, with and without a lead?

Research for [#370](https://github.com/shrujancheruku/claude-orchestrate/issues/370) (map [#368](https://github.com/shrujancheruku/claude-orchestrate/issues/368)). Sources read 2026-11-08: the repo at `1a49961` (`skills/run/SKILL.md`, `skills/lead/SKILL.md`, `scripts/lead-route`, `scripts/runlog.py`, `scripts/worker-report`, `docs/agents/triage-labels.md`, `GLOSSARY.md`, ADR-0008, `.claude/orchestration.md`), GitHub's [issue event types](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types) docs, this repo's issue events and timelines, and the local run log (`.claude/orchestrate-profiles/events.jsonl`, 313 lines; `passes.jsonl`, 56 lines).

## Answer

- **With a lead, a stop has a clean start and end on the tracker.** Start: `labeled needs-lead` and a `commented` event whose body starts with `> *Stopped for the lead.*` (run adds the label, then posts the comment). End: `unlabeled needs-lead`. The lead's answer comment has no marker, so the label removal is the end to read. Both come from the issue timeline API with `created_at`.
- **Without a lead, the start is on the tracker but the end isn't marked.** Start: `labeled needs-info`, `unlabeled ready-for-agent`, `unassigned`, and a comment starting `> *This was generated by AI during triage.*`, all close together. The developer's answer has no defined form. The best signal is `labeled ready-for-agent` (or `unlabeled needs-info`) after that start. The re-claim (`assigned`) comes later and adds the orchestrator's pickup lag on top of the developer's wait. A comment alone can't be used: it has no marker, and the developer, the lead and the orchestrator all post as the same account.
- **Gate waits, third review rounds and ADR conflicts without a lead leave no start marker on the tracker.** A merge-gate wait shows as the gap from the approving review (only when reviews are posted) to `merged`, but nothing says it was a gate. A start gate leaves nothing until `assigned`. A third round's start is a `reviewed` event whose body starts `Round 3 · verdict: changes`, but the developer's decision is made in chat. An ADR conflict with no lead is never labelled.
- **A held ADR-conflict PR in lead mode is fully on the tracker.** Start: `labeled needs-lead` and a comment starting `> *ADR conflict held for the lead.*`. End: `unlabeled needs-lead`, then `merged` on the PR. What tells it apart from a stop is which marker comment is newest, the same rule `lead-route` uses (`adr_hold_of`).
- **The run log covers what the tracker can't, but only coarsely.** `events.jsonl` has a `worker-report` event (`outcome: valid`, `status: stopped`, `stop_reason`) for each stop, timed when the orchestrator classified it. That is the earliest timestamped start, and the only start for stops that never reach the tracker (`permission-denied`, stops the orchestrator answers itself). There is no run-log event for an answer, a resume, `UNCAP`, `FALLBACK` or a gate yes. `passes.jsonl` records `claimed: {ticket: "waiting"}` at each pass, so a wait shows only to pass resolution, and without its reason.
- **Two caveats.** Every tracker event has the same actor (`shrujancheruku` made 1669 of 1775 issue events here; the rest were bots), so who acted has to be read from labels and markers, never from `actor`. And every run-log event currently has `session: null` ([#341](https://github.com/shrujancheruku/claude-orchestrate/issues/341)), so `runlog.read_events` falls back to the time window.

## Per-case table

"Timeline" means `GET /repos/{o}/{r}/issues/{n}/timeline` (the ticket, or the PR for `reviewed`/`merged`). Every row there carries `created_at`, or `submitted_at` for reviews.

| Case | Start | End | Readable afterwards from |
|---|---|---|---|
| Lead stop (ambiguity) | `labeled needs-lead`; comment `> *Stopped for the lead.*` | `unlabeled needs-lead` (lead: answer, remove label, nudge) | Timeline: both ends |
| Lead stop, then worker resumes | as above | next `worker-report` event for the ticket (`RESUME` is a SendMessage) | Start: timeline. Resume: `events.jsonl` or transcript only |
| Lead stop → `UNCAP` (30 min) | as above | not an end: the slot frees, the stop continues | Transcript only (lead-route output) |
| Lead stop → `FALLBACK` (lead gone) | as above | becomes a no-lead stop: `unlabeled needs-lead`, `labeled needs-info`, `unassigned`, a comment with **no fixed marker** | Timeline (label pair + unassign) |
| Lead stop → split (`HANDBACK`) | as above | `blocked_by_added`, `unlabeled needs-lead`, then `unassigned` and a comment naming the branch | Timeline |
| Lead stop → obsolete (`ABANDON`) | as above | `labeled wontfix`, `closed`, then `unassigned` | Timeline |
| No-lead stop (ambiguity) | `labeled needs-info`, `unlabeled ready-for-agent`, `unassigned`, comment `> *This was generated by AI during triage.*` | developer's relabel: `labeled ready-for-agent` / `unlabeled needs-info`; pickup: `assigned` | Timeline, but the marker comment is shared with the triage skill, so pair it with the `unassigned` |
| Human-only step | same, with `ready-for-human` | `closed` by the developer, or a relabel | Timeline |
| `permission-denied` stop | nothing on the tracker | the next `worker-report` (`pr-opened`) | `events.jsonl` only (3 real ones: #325, #349, #337, 2026-11-08 06:12–06:24) |
| Start gate | nothing on the tracker | `assigned` | Start: transcript only |
| Merge gate | approving `reviewed` (`Round N · verdict: approve`) when posted; else nothing | `merged` | End: timeline / `events.jsonl` `merge merged`. Start: timeline only if posted; the reason (gate) comes from the PR's files against the config's merge gates |
| Third review round | `reviewed` body `Round 3 · verdict: changes` (when posted) | developer's call in chat (lead mode: relayed by SendMessage) | Start: PR timeline if posted. End: transcript only (a later push, review, merge or close is a proxy) |
| ADR conflict, lead live (`HOLD-PR`) | `labeled needs-lead`; comment `> *ADR conflict held for the lead.*` | `unlabeled needs-lead`, then `merged` | Timeline |
| ADR conflict, lead gone (`ASK-DEV`) | as above | `unlabeled needs-lead` by the developer | Timeline |
| ADR conflict, no lead from the start | nothing labelled | merge or a follow-up | Transcript only |

## Evidence

### What run and the lead write

- **Lead stop.** "Add `needs-lead` and keep the claim, `ready-for-agent`, the slot and the touch map. Post a stop comment that starts with the line `> *Stopped for the lead.*`, then the worker's question and the branch. Then nudge the lead" (`skills/run/SKILL.md`, Worker reports). GLOSSARY *Stop comment*: "`scripts/lead-route` reads it for the stop's time."
- **The lead's end.** "Answer with a ticket comment, remove `needs-lead`, then nudge the orchestrator", with outcomes narrow/reword, split (blocking edges, run hands it back), follow-ups, or obsolete (close `wontfix`) (`skills/lead/SKILL.md`, Settling a stop). The answer comment has no prescribed first line.
- **What lead-route keys on.** `stop_of` takes the newest comment whose first line is `STOP_MARKER`. A `RESUME` needs "no needs-lead … stop comment newer than its last report", so to run the label's removal *is* the answer. `UNCAP_AFTER = 30 min` after the stop comment. `ESCALATE` uses body edits and `## Agent Brief` comments via GraphQL `userContentEdits`. The REST timeline has no edit events; a comment has only `updated_at` (the docs list no body- or comment-edit event).
- **FALLBACK** (run skill): "swap `needs-lead` for `needs-info`, comment that the lead was gone, unassign": no marker string.
- **No-lead hand-back** (run skill, `valid stopped`): label `needs-info` (or `ready-for-human`), "Remove `ready-for-agent` … and unassign it", comment "starting with the line `> *This was generated by AI during triage.*`", "Put it to the user." Nothing says how the answer comes back. Note: GLOSSARY reserves **Hand-back** for the merge sweep's `HANDBACK` line, so "handing back to the tracker" is the right phrase for this one.
- **ADR conflict** (run skill, `valid pr-opened`): in lead mode add `needs-lead`, comment `> *ADR conflict held for the lead.*`; `HOLD-PR` skips merge "while `needs-lead` is on the ticket; once the lead removes it the PR merges with no further signal". "With no lead from the start, conflicts go to the developer directly and nothing is labelled."
- **Waiting** (GLOSSARY): "A claimed ticket blocked on the user: a gate, a question or a third review round." The run skill lists waiting as the orchestrator's own state, "layered on these from your context; `claims` never reports them". Gates and the third round are put to the user, in lead mode relayed by SendMessage ("Escalate to the user"). None of that touches the tracker.

### GitHub API

- From the [issue event types](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types) docs: `labeled`, `unlabeled`, `assigned`, `unassigned`, `closed`, `reopened` appear in both the issue events API and the timeline, with `actor` and `created_at`. `commented` and `cross-referenced` are **timeline only** (`commented` carries `body`, `created_at`, `updated_at`). `reviewed` is **timeline only, PRs**, with `state`, `body` and `submitted_at`. `ready_for_review` and `convert_to_draft` are PR events. The docs list no event for an issue body or comment edit.
- So a profile reads each ticket's timeline (comments and labels in one call), and each PR's timeline for `reviewed`/`merged`. The repo-wide `issues/events` feed has no comments.
- Repo-wide event counts here: 358 `labeled`, 56 `unlabeled`, 162 `assigned`, **0 `unassigned`**, 0 `needs-lead` labels ever. Searching for `Stopped for the lead` or `ADR conflict held` finds only #370's own body. **No lead stop and no orchestrator hand-back has happened on this tracker yet**, so the lead rows above come from the skills and `lead-route`, with no real example to check them against.

### Real examples

- **#5 / #317 (`needs-info`)**: `labeled needs-info` (2026-11-03T16:10:47Z; 2026-11-08T05:49:41Z, together with `unlabeled needs-triage`), then a comment. These come from triage, not from a worker's stop: no `assigned`/`unassigned`. #5 ended with `closed` 4 days later and no relabel, so a no-lead stop can end in a close.
- **#111 (`ready-for-human`)**: `labeled ready-for-human` 16:39:28, `assigned` 16:51:36, comment `## Resolution` 16:52:49, `closed` 16:52:51: the developer did it and closed it.
- **Merge gate, posted reviews: #279 / PR #331** (touches `hooks/**`, a merge gate in `.claude/orchestration.md`): `reviewed` "Round 2 · verdict: approve · tier: L" 2026-11-07T21:08:51Z, pass log `{"279": "waiting"}` at 21:41:29, `merged` 2026-11-08T05:19:59Z. The tracker shows the ~8 h gap. Only the pass log and the config say it was a gate wait.
- **Merge gate, no posted review: #55 / PR #82** (guard): the pass log shows `{"55": "waiting"}` from 12:18 to 13:43 on 2026-11-04. PR #82's timeline holds only cross-references and `merged` 14:17:23. The wait's start is not on the tracker at all.
- **Review rounds**: the reviewer's posted review body starts `Round <n> · verdict: <v> · tier: <t>` (PR #331), so round count and verdict can be read from `reviewed` events when `Post reviews` is on.

### Run log

- `runlog.OUTCOMES` kinds: `gate`, `ci`, `merge`, `replay`, `worker-report`, `threads`, `frontier`. Nothing for labels, comments, lead-route verdicts or user answers. Here, `gate` is the **Script gate** (mechanical), not a user gate (GLOSSARY *Gate* vs *Script gate*).
- `worker-report` logs each verdict with `status` and `stop_reason` (and `denied_command` for permission-denied). Local log: 7 `worker-report valid` events, of them 3 `stopped permission-denied`.
- `passes.jsonl` `claimed` values seen locally: `building` 67, `in review` 22, `waiting` 16. The `waiting` state carries no reason (gate, question, round 3).
- `read_events` keeps session-less events only inside `[start, end]`, and every event currently has `session: null` (#341).

## Implications for the profile (not decided here)

- Stop wait **with a lead**: `labeled needs-lead` → `unlabeled needs-lead`, read from the ticket timeline. Clean, and it measures the lead plus the developer.
- Stop wait **without a lead**: from the hand-back cluster (`unassigned` + `needs-info`) → `labeled ready-for-agent`, or `closed`. A ticket still `needs-info` at profile end is open-ended. Re-claim (`assigned`) is a separate "pickup" figure.
- For like-for-like comparison, the `worker-report stopped` event is a common start in both modes. Waits that never reach the tracker (gates, round 3, no-lead ADR conflicts, permission-denied) are measurable only at pass resolution from `passes.jsonl`, unless run starts writing a marker comment or run-log event for them, which would be a change.
