# orchestrate: the full guide

Everything about installing, configuring and running the plugin. For the overview, see the [README](../README.md); for the terms, the [glossary](../GLOSSARY.md).

## What it is

A Claude Code plugin that works through a backlog of GitHub issues in parallel, picking up the tickets that [Matt Pocock's skills](https://github.com/mattpocock/skills) (`to-tickets`, `to-spec`, `triage`) leave `ready-for-agent`. Your main session acts as the **orchestrator**: it decides the order of work, hands each ticket to a **worker** in its own git worktree, pushes searches down to a cheaper agent, reviews each PR at a depth sized to it, and merges by your repo's rule. Anything that is yours to decide waits for you.

```
orchestrator (your session, e.g. Opus)     order, briefs, verdicts, merges, gates
 ├─ worker        Sonnet, own worktree      one ticket → one PR
 ├─ reviewer      Haiku (S) / Sonnet (M, L high effort) one PR against its ticket, read-only, posts its review
 └─ scout         Haiku, read-only          tracker and CI facts
```

## Install

```sh
/plugin marketplace add shrujancheruku/claude-orchestrate
/plugin install orchestrate@claude-orchestrate
```

From a local clone, use the clone's path in place of `shrujancheruku/claude-orchestrate`. While developing, load it without installing: `claude --plugin-dir /path/to/claude-orchestrate`.

Needs `git` 2.38 or later (the post-merge sweep checks conflicts with `git merge-tree --write-tree`; on older git it says so and skips the sweep), `gh` (signed in), and `python3` 3.9 or later (plugin scripts and hooks: Python 3.9+, stdlib only). Run `/setup-matt-pocock-skills` in the repo first: orchestrate reads the tracker and domain docs it writes to `docs/agents/`. Without them, setup falls back to a backlog defined in the config.

## Use it in a repo

1. **`/orchestrate:setup`** scouts the repo (tracker, commands, layout, conventions, anything that would collide across parallel worktrees) and asks you the decisions in one round: backlog source, slots, gates, merge authority, models, review tiers. It infers shared files and their per-PR rules from your docs and merge history, advises on risk paths, and prints a recommendation if `autoCompactWindow` is above 200K (it never edits your settings). It writes `.claude/orchestration.md` (the **config**) and a `.worktreeinclude`.
2. **`/orchestrate:run`** runs one **pass**. It rebuilds state from the tracker, reviews and merges finished PRs, fills free slots with workers, and reports a table of tickets. Passes are safe to repeat and to start in a fresh session, because the state lives in the tracker, not in the conversation.
   - `/orchestrate:run status` reports without dispatching or merging.
   - `/orchestrate:run <ticket>` narrows a pass to one ticket; `/orchestrate:run <parent issue>` to its sub-issues.
   - Plain `/orchestrate:run` is the only supported flow. After its pass the orchestrator ends its turn and wakes only on worker and reviewer completions, on `watch-ci` lines (CI settling) and on its own usage-limit cron hops. It reads the config and tracker docs once per session, and again after a compaction summary, keeps every command's output bounded, and ends a wake with one line, or nothing when nothing needs you. It shows the full table only when a pass ends or something needs you, and a pass that ends with nothing in flight says so and stops.
   - **Discovered work.** A worker or reviewer that finds work the backlog is missing (a pre-existing bug in untouched code, a needed refactor, an unplanned dependency) records it in a `## Discovered work` section on its PR body or posted review, one line per item (`- <what is missing> — <where> — <why it matters>`), instead of fixing it or raising a `[minor]` finding. It never blocks the PR. Their reports carry `discovered: <n> — <gist>`, and the end-of-run summary lists the PR URLs that carry any, so you can triage them.
   - Add `--greedy[=N]` to a full or parent pass to size the slot count from how many tickets can run at once, up to N (5 by default): see [Choosing a slot count](#choosing-a-slot-count).
   - Add `--profile` to any of these to profile the session as it runs: see [Profiling](#profiling).
   - The two combine: `/orchestrate:run --greedy --profile` runs greedy and profiles it, which is how to find out whether greedy paid off on your backlog.
   - **Starting the orchestrator.** `/orchestrate:start [--greedy=N | <ticket>] [--profile] [--print]` from any Claude session in the repo launches it in the background and prints the session id and the resume command. `scripts/launch [--greedy=N | <ticket>] [--profile] [--bg] [--resume <sessionId> | --resume-latest] [--print]` does the same from a terminal (foreground by default). Both exit 2 with one line when a live `orchestrator` session exists. Resuming a `background` row passes no session flags (Claude Code keeps the saved options, and flags would fork an idle copy): the line is `claude --resume <id> --bg` plus the session's original `/orchestrate:run` prompt, read from its saved transcript or built from the ticket or `--greedy` you pass, so the pass starts on its own. With neither, one stderr line gives the `claude attach <id>` and `/orchestrate:run` line to type, because `/orchestrate:run` is user-only. A `--permission-mode` that differs from the saved one is refused (exit 2). An interactive row keeps the flags. A background resume reuses its saved plugin dir, so a merged plugin change reaches it only through a fresh launch. `scripts/launch` owns the launch line: its header explains the flags, and [Permission mode](#permission-mode) says why it passes the mode and the auto-mode switch.

### Concepts

- **Ticket:** a GitHub issue `scripts/frontier` lists as takeable: open, `ready-for-agent`, unassigned, unblocked, not a parent (no sub-issues, open or closed) and not the lead's. Taken in ascending issue number, the order `to-tickets` publishes them in. The tracker operations and label strings come from `docs/agents/`. A ticket a worker can't finish goes back to the tracker as `ready-for-human` or `needs-info`.
- **Slot:** one ticket in flight. The config sets how many. Two tickets run at once only when their **touch maps** (the files the scout expects each to change) don't overlap outside the shared files; an **exclusive hold** keeps a path to one ticket until it merges. A ticket another session's live worker is building holds the files that worker has changed so far, committed or not, so this session won't start an overlapping ticket beside it. An open release-please PR (head branch starting `release-please--`) holds nothing, so its four release files never appear as held; a human PR that touches them is still held. The open PRs' file lists are cached in `.claude/orchestrate-snapshot.json`, keyed by head commit: `holds` and `gate` read the open PRs live (one list call), use the cached list for every PR whose head matches, fetch only the misses and write them back, so a pass costs one file-list read per PR (plus one per push), not one per `holds` call. A missing or corrupt file means every list is fetched. An open PR's changed files join its ticket's touch map for holds, so an edit outside the map still holds, and a building ticket's worktree changes join its map the same way; `gate` prints `touch map: +<n> files outside the map` when a PR has drifted.
- **Domain docs:** workers and reviewers follow the glossary and ADRs that `docs/agents/domain.md` points to. A PR that contradicts an ADR without saying why is a blocking finding.
- **Gate:** a ticket, label or path that waits for your go-ahead to start or to merge.
- **Tier:** review depth from the PR's diff and the config's thresholds (the `tier` line `gate` prints before its `next:` line; a `size:` label on the ticket only raises it, never lowers it). S is a Haiku checklist review; M is a Sonnet correctness review; L is a Sonnet review at high effort whose risk notes go in the posted review for humans; the orchestrator reads no risky files itself. A round-1 `approve` with minors gives the worker the minors to take or leave, and CI alone gates the merge. Later rounds continue the same reviewer, and a push after approval goes back to it only when it touches a risk path or exceeds the S thresholds. With `Post reviews: yes`, the reviewer posts each round on the PR itself as a comment review (verdict in the body, findings inline) and hands back only the verdict, counts and the review URL; the worker reads the findings from the PR, and a finding whose file is outside the diff sits in the review body, where the worker answers it with a PR comment (it has no thread to close). With `no`, or when a post fails, the reviewer returns the full findings. It's always a comment, because GitHub won't let your account approve its own PR. When `merge` refuses an approved PR only for unresolved threads, every one is a `[minor]` and its worker is gone, the orchestrator resolves them itself with `threads <pr> resolve <id> --left "the worker finished; left for a follow-up"` and merges, instead of dispatching a new worker to post replies.
- **Brief:** the pointer-only prompt a worker gets (see `skills/run/brief.md`). The ticket stays the spec.

## Permission mode

Run the orchestrator in `acceptEdits` or `bypassPermissions`, never in `auto`. Workers are subagents, and a subagent inherits the main session's permission mode (a `permissionMode` in a plugin agent's frontmatter is ignored). Under `auto`, every worker action goes through the auto-mode classifier, and the classifier skips a subagent's `Edit` and `Write`: the worker's first edit in its worktree fails with "the server-side auto mode classifier gave no verdict (it skipped this action)", marked as a hard failure not to retry. Neither the guard's hook allow, an allow rule, the parent's mode, a refreshed auto-mode environment nor a `defaultMode` in settings reaches that skip (#378).

`scripts/launch` and `/orchestrate:start` already start the orchestrator the working way, so use them:

- `--permission-mode <mode>` (default `acceptEdits`). In `acceptEdits`, workers' edits inside their worktrees pass without a prompt, and the guard's `allow` covers the routine `git` and `gh` steps. `bypassPermissions` also works and is wider.
- `--settings '{"disableAutoMode":"disable"}'`, for this one session only. It removes auto mode from the session, so subagents take the parent's mode instead of falling into the classifier. With `--bg` (and with `bypassPermissions`) `scripts/launch` adds `crossSessionInbound` to the same JSON, so a background orchestrator can hear the lead. Your own sessions keep auto mode. Three Claude Code facts sit behind this line:
  - **Cross-session delivery depends on the permission-mode class** (bypass versus prompting: `auto`, `acceptEdits`, `dontAsk`, `plan`). A receiver holds a message from the other class behind a "Deliver this message?" dialog that only a human at its terminal can answer, and a `--bg` session then shows `waitingFor: permission prompt`. `crossSessionInbound: "accept"` is read only from managed settings, `--settings` or user settings (a project value applies only when stricter), which is why `scripts/launch` passes it with `--settings`.
  - **`claude --bg` under `bypassPermissions`** needs the bypass disclaimer accepted once interactively (`claude --dangerously-skip-permissions`); until then the background launch fails.
  - **`autoMode.environment`** is read only from `~/.claude/settings.json`, managed settings or `--settings`; a block in a project `.claude/settings.json` is ignored. `disableAutoMode` takes the string `"disable"`, not a boolean, and is read at session start.
- `--plugin-dir <link>`, when the plugin runs from a checkout. The flag names a stable path, `$XDG_CACHE_HOME/orchestrate/plugin/r-<hash of the checkout>/current` (else under `~/.cache`), a symlink to the snapshot below (#728; the read rule in `--settings` names the whole snapshot cache directory, so a flip strands no read; a fresh launch repoints the repo's link under any other running session of that repo, and only ever to merged `origin/<default>`). A real launch repoints it at the snapshot of `origin/<default>`; `--print` never moves a link that exists; pruning never removes the snapshot a link points to. `scripts/launch` exports the plugin (`.claude-plugin/`, `hooks/`, `agents/`, `skills/`, `scripts/`, `viewer/`) at `origin/<default branch>` into `$XDG_CACHE_HOME/orchestrate/plugin/<sha>/` (else `~/.cache/orchestrate/plugin/<sha>/`), reuses it while the sha is unchanged, keeps the 3 newest (a real launch prunes the rest, never one used within a day, so a running session keeps its plugin dir) and prints one stderr line naming the sha. The same `--settings` JSON carries one allow rule, `Read(//<snapshot>/**)` (`//` is Claude Code's prefix for an absolute path), so the skills and agents can read their reference files there without a prompt (#617). Reads of the snapshot are allowed and edits are not: the settings hold no Edit, Write or Bash rule, because the snapshot holds the running `hooks/guard.py`, and `--add-dir` is never used since it would widen edits too. Agents call the plugin's scripts through the snapshot as well: the run skill passes each worker, reviewer and scout a `Plugin root:` line, and the guard approves `<Plugin root>/scripts/<name>` and refuses the checkout's copy. It never points the flag at the checkout: Claude Code treats every file under an inline plugin's root as a sensitive file, and the worktrees sit inside the checkout, so every worker and orchestrator edit would prompt even in `acceptEdits` (#581). The trade-off: a merged change to `hooks/`, `agents/`, `skills/` or `scripts/` reaches a background run only through a fresh launch (stop the orchestrator, then `scripts/launch --bg <flags>`); a background resume keeps its saved snapshot and `scripts/launch` says so in one stderr line (`resume keeps snapshot <old>; origin/<default> is <new>: a fresh launch picks it up`) when the plugin tree has moved (it finds the snapshot in the session's saved transcript, since `claude agents --json` rows carry no plugin dir; with none there it says it cannot tell). A launch run from a snapshot (the lead's) exports afresh from the checkout the snapshot came from (recorded in its `.source`), and reuses the snapshot only when that checkout is gone, instead of refusing. A marketplace install needs no snapshot and no flag.

  A guard fix that merges mid-run does nothing for the running session (#727). Claude Code loads a `--plugin-dir` plugin once, at session start or `/reload-plugins`; skills and agents substitute `${CLAUDE_PLUGIN_ROOT}` when they load, and hooks on a copied plugin keep the previous path until `/reload-plugins` ([plugins](https://code.claude.com/docs/en/plugins/loading.md)). The developer's hand-run on #727 shows hooks do follow a symlinked `--plugin-dir`, so the run loads its plugin through the stable link above and a guard fix reaches it live (#728). After a PR that touches `hooks/**` or `.claude-plugin/**` merges (by `scripts/merge`, or by the developer by hand and then cleaned up with `scripts/merge`), `merge` exports the snapshot of the merged `origin/<default>` (never a PR head) and repoints the link atomically (a temporary symlink, then `rename`), printing `snapshot: <old>..<new>`; hook scripts apply from the next call. Any other PR leaves the link alone. Skills, agents and `hooks/hooks.json` are loaded once per session, so when the old..new diff touches one of them `merge` also logs a `snapshot` event with outcome `stale` and the new `origin/<default>` sha, and prints a `snapshot-stale <sha>` line; a diff of hook scripts alone records nothing. The same stale record is the fallback when the link cannot be moved (or a launch left no link). A background resume keeps its old plugin dir (the flag it was saved with), which is now the stable link, so a resume picks up the repointed hook scripts too; a relaunch for skills or agents is still a fresh `scripts/launch`. It does so only for the repo the running snapshot was exported from (the fresh launch's `launched` event names that checkout as `source`; with no such event, as on a marketplace install, or in another repo, nothing is logged), and not when the loaded sha already holds `origin/<default>`'s plugin tree (a PR merged before the relaunch, cleaned up after). While it stands `scripts/frontier` prints one `relaunch: snapshot behind main` line in place of the tickets, so no new worker is dispatched and the in-flight work drains. A fresh `scripts/launch` (not a resume, which keeps its saved snapshot) logs `snapshot launched` and clears it. A `launch --resume` of a background row says on stderr when its snapshot is behind (`resume keeps snapshot <old>; origin/<default> is <new>`), and a relaunch for a plugin change needs a fresh launch, never a resume.

If you start the orchestrator by hand, pass both flags: `claude --name orchestrator --permission-mode acceptEdits --settings '{"disableAutoMode":"disable"}' "/orchestrate:run --greedy"` (add `--plugin-dir <path>` when the plugin runs from a checkout). A developer who never uses auto mode can set `"disableAutoMode": "disable"` in `~/.claude/settings.json` instead; setup never edits it. If you see the "gave no verdict" text on a worker's edit, the session is in auto mode: restart it with the two flags above.

The guard stays the fence in every mode ([ADR-0002](adr/0002-guard-own-lexer-fail-closed.md)). It assumes `acceptEdits` or `bypassPermissions`; auto mode is unsupported for the orchestrator session.

A background orchestrator (`claude --bg`) has nobody to answer a prompt, so it needs no `bypassPermissions` for its reconcile pass: in `acceptEdits` the guard approves a chained command whole when every part is one of the plugin's read-only pass scripts (`snapshot`, `rebuild-state`, `claims`, `frontier`, `holds`, `gate`, `ci-times`, `watch-ci`, `worker-report`, `lead-route`, `lead-brief`, with `--repo .` as the only path, `snapshot --out` only for `.claude/orchestrate-snapshot.json`, and no write flags; `launch`, `sandbox-git`, `rescue` and `verify` are never approved in a chain) or `merge`, `threads`, `board` in their exact forms (by resolved path, written as `"${CLAUDE_SKILL_DIR}/../../scripts/<name>"` or through a variable assigned earlier in the same command), `tail`, `head`, `echo`, `printf`, `sort`, `grep`, `wc`, `cat` of a file under `.claude/`, or a variable assignment, joined by `;`, `&&`, `|` or newlines, with no redirect but `2>&1`, and `sort` and `printf` carrying no output or variable options. A variable may only name a place inside the plugin. Anything else in the chain (`rm`, `curl`, `||`, a heredoc, a variable pointing outside the plugin's `scripts/`) leaves the whole line to the permission layer, which prompts. `merge`, `threads` and `board` keep their exact argument forms inside a chain (#407).

## Cost

- Each role runs on the cheapest model that does it well. Set them per repo in the config's **Models** table.
- Searches and log reads run in Haiku contexts, so the orchestrator's and workers' contexts stay small.
- **Worker report check:** on every worker completion the orchestrator pipes the completion text to `scripts/worker-report <ticket> --branch <branch>`, which prints one verdict (`valid pr-opened`, `valid stopped`, `interim`, `duplicate`, `not-a-stop`, `not-a-pr-opened`, `missing-report`, `limit` or `error`) and appends a `worker-report` event to the run log, carrying the report's `refused:` lines (each tool call the harness or guard refused; `[]` for `refused: none`). A stopped worker's report carries a `stop-reason:` line from a fixed list; the PR number and head come from the host, never from the report. A `permission-denied` stop (the harness refused `gh pr create`) also carries `denied-command:`; the ticket keeps its claim and slot, shows under Waiting on you on the board, and the user runs the command with `!` or allows it. The orchestrator never runs it. A `transient` stop (a host failure such as a GitHub rate limit; it carries `failed-command:` and, when known, `retry-after:`) is retried by the orchestrator without the developer, at most twice per failed command; a `permission-denied` or `human-only` report that names a rate limit or a wait-until time is reclassified `transient`. With `--reviewer` (`scripts/worker-report <pr> --reviewer`) it classifies a reviewer's report instead: no PR lookup, no event, and a report with no `suite:` line (or an empty or unrecognised one) is `incomplete`, sent back to the reviewer once. A `worktree-gone` stop (a continued worker whose worktree the harness removed after a no-edit stop) is answered with a fresh worker on the same branch, and the orchestrator runs `claims <ticket>` and checks for `worktree gone` before any SendMessage continuation of a ticket with no PR, so it never reaches that stop.
- **Review threads:** `scripts/threads <pr>` lists a PR's unresolved review threads (`--all` adds resolved ones with their closing reply), and `resolve <thread>... --fixed <sha>` / `--left "<why>" (--followup <issue> | --no-followup)` and `reopen <thread>... --why "<why>"` reply on each thread, then resolve or reopen it, logging a `threads` event per thread. Several ids in one call cost two GraphQL requests in all (the replies, then the resolves, one aliased mutation per thread), so resolve every thread of one reason together; `--verbose` prints `writes: <n>` on stderr. The reviewer's `reopen` stays one id per call. Every review finding is a thread, closed with `fixed in <sha>` or `left: <why> (follow-up #<n>)`, so the PR shows what was taken and where what was left went: a `--left` names the one follow-up ticket for the PR, or `--no-followup` says none, and `threads <pr> followup [<thread>...] [--gist "<text>"]` files that one ticket (first line `Left from PR #<pr>`, labels `needs-triage` and `lead`, each thread as `path:line` with the reviewer's text word for word; an existing open one by a trusted author is appended to, so a second call files nothing), prints its number and adds the `Left for #<n>` line to the PR body; the PR body carries a `Left for #<n>` line.
- **Script gate:** before any reviewer is dispatched, `scripts/gate <pr>` prints the PR's head commit first (the join key with `watch-ci`'s line, so review starts only when CI is green on a head whose gate passed), then checks the PR's mergeability with its base (conflicts only: a branch that is merely behind passes, and `merge` updates it at merge time, exit 5), its title against Conventional Commits, overlap with held paths (it runs the holds library, `scripts/holds.py`, in process, the one source of the held-path rule; two open PRs on one path are an ordering, not a failure: the lower-numbered PR passes, and the younger prints `waits for #<ticket> (PR #<n>) to merge` and exits 3, to be run again after that PR merges, while a path held by a ticket with no PR yet still fails), dependencies merged (the PR's ticket has no open blocker and the PR is based on the default branch), no secrets added (env, key and credential files, private-key and token lines in the diff), that a changed lockfile has a changed manifest, and that every GraphQL `query` string the diff adds or changes in a Python file or extensionless script (found from the AST of its head and base versions; an f-string is never read) runs once, read-only, through `gh api graphql` with fixture values (the repo's owner and name, the PR's number for an `Int` (`1` for one passed as a `first:` or `last:` page size, which GitHub caps at 100), a placeholder for another required variable, optional variables left out) and returns no GraphQL error (a missing node is not one), while a `mutation` is never executed and its fields are checked against the schema's `Mutation` type, all built in, and each command a **Repo-specific check** in the config marks with ``run: `cmd` `` (plain backticked text is never run). It prints one line per check like `verify`, appends a `gate` event, and a failure goes straight back to the worker without counting as a review round.
- Review fixes go back to the worker that wrote the PR, so its context is reused instead of a new agent starting.
- Briefs share a fixed preamble, so workers share a prompt-cache prefix.
- Parallel agents multiply token use. Fewer slots cost less; the slot count is your throttle. See [Choosing a slot count](#choosing-a-slot-count).

## Choosing a slot count

Setup recommends 2. Each extra slot adds a worker's tokens and its reviews, raises the odds that a usage limit pauses several tickets at once, and adds reports and reviews to your main session, which handles them one at a time and is usually the first thing to saturate. The gain is wall-clock time, and only when the backlog's tickets are independent.

Every full pass suggests a change of one slot, between 1 and 5: lower after a usage limit or when overlaps left a slot idle, higher when every slot is full and the next ticket wouldn't overlap. It changes the config only when you say yes. The reasoning is in [ADR-0001](adr/0001-slot-count.md).

`/orchestrate:run --greedy[=N]` sizes the count for you instead. Each pass dispatches every takeable ticket whose touch map overlaps no held path, up to a cap of N (5 by default, 1 to 8), and never stops a worker in flight. It holds for the session, never edits the config, drops back to the config's count after a usage limit until the reset, and makes no per-pass suggestion. Each report starts `Greedy · cap N · running M`. The reasoning is in [ADR-0007](adr/0007-greedy-slots.md).

Use greedy when the backlog has several independent tickets and you have plan headroom to spend on finishing sooner: a batch of small fixes, or the leaves of a spec once their blockers have merged. Keep the config's count when tickets mostly touch the same files (overlap holds them at any count, so greedy gains nothing) or when usage is tight, since every running ticket adds a worker and its reviews. `--greedy=N` sets a lower or higher cap for one session without touching the config.

**Rate limits.** A greedy run can hit GitHub's secondary rate limit (many `gh` calls at once). Every script waits it out: `scripts/github.py` retries up to 5 times, sleeping the `retry-after` seconds when `gh` shows them, else a minute (the time it records for the others). The hourly quota running out is not retried; the call fails at once with the reset time. A script's rate-limit hit is also written to `$XDG_CACHE_HOME/orchestrate/github-ratelimit-<host>.json` (`~/.cache` when unset), shared by every agent on the machine, so every other script waits too, and the error says the HTTP status and headers. A script sleeps at most about 75 seconds in total (`ORCHESTRATE_GH_WAIT` overrides it); a wait that would pass that is not slept: the script exits 2 at once and ends `next: retry-after <time>` (the error text says `rate limit until <time>`), and the caller retries after that time. After the fifth try it exits 2 too. A GitHub 5xx (`HTTP 500` to `504`) is retried the same way on a short ladder (2, 4, 8, 16 seconds) within the same budget (`ORCHESTRATE_GH_WAIT`), and `ORCHESTRATE_GH_5XX_TRIES` caps its tries. Only a read, or a write its caller marks idempotent (closing an issue, deleting a branch, a board card's stage or position), is retried: a 5xx can arrive after GitHub applied the write, so a creating POST, a merge, a comment or a delete/archive batch fails at once and the caller re-reads. A 4xx other than a rate limit is never retried. For a read, a truncated reply (`unexpected end of JSON input`) or a connection reset is retried on the same ladder; a write is never retried on those. A 5xx that outlasts the tries or the budget is its own outcome, `servererror`: the script exits 2 with the status and the last body line, and no `retry-after`, because no reset is coming (`watch-ci` counts it as one failed tick). The 75-second budget is per process, not per call, so several rate-limited calls in one script run share it; `watch-ci` and `merge`, which loop for hours, reset it each tick. A pull request with more than 1,000 checks, or one that closes more than 100 issues, exits 2 instead of judging a partial list.

## Keeping slots full

Three things keep the slot count from silently shrinking (#716). A successful `merge` ends `next: frontier`, and the run runs the frontier and fills the freed slot in the same turn. A `parked` claim (a ticket whose PR `park-pr` took out of the merge queue) keeps its claim but holds no slot: `claims --slots` and `frontier --slots` end with `slots: <building>/<cap> building, <k> parked`, and only the building claims count against the cap. And with a lead live, `lead-brief --watch` wakes the lead with `idle-slot: <building>/<cap> building; dispatchable: #<n> ... (<m>m)` when building claims stay under the cap for longer than the idle window while a takeable ticket that no `holds` check blocks waits; the lead nudges the orchestrator with that line. The pass digest also carries the `slots:` line (`lead-brief --velocity`) and lists a held PR that blocks several takeable tickets as an ask for you. Holds are read from each ticket's `Lands in:` paths; a ticket with none counts as free.

The optional `## Velocity` section of the config tunes it, and a missing section means the defaults:

- `Idle window:` how long a slot may sit free with work waiting before the lead is woken (default `10m`).
- `Expensive hold:` how many takeable tickets one held PR must block before the digest asks you about it (default `3`).
- `Velocity watch:` `on` (default) or `off`, which stops the `idle-slot:` wake.

## The guard hook

`hooks/guard.py` runs before every Bash call and every file edit (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`) and refuses only for this plugin's agents (`agent_type` `orchestrate:<role>`); the orchestrator's own session (no `agent_type`) is refused only for a hand-made wait (`sleep`, `timeout`-wrapped `sleep`, `read -t`, or an `until` loop around `gh`: waits go through `watch-ci` as a Monitor, #407; only for the orchestrator's session, found by the first command of its transcript being `/orchestrate:run`: the lead, a developer's own session and a session whose transcript the hook cannot read get no decision from this rule) and otherwise given the routine-step approval described below:

| Role | Refused |
|---|---|

Every role also refuses `scripts/merge` (the orchestrator's merge script, which re-checks the PR until it is MERGED, then deletes the branch, closes the ticket and removes the worktree, and the PR's detached `pr-<n>`, `pr-<n>b` and `pr-<n>-<suffix>` scratch worktrees a reviewer left), run as a command.

Given `--approved-head`, `scripts/merge` first decides the merge rule itself and merges nothing unless the PR is ready: CI pending, failed or cancelled on the head (a PR with no checks counts as pending when the head has workflow files, reported as `ci: pending`, and as green, reported as `ci: none configured`, when it has none), an open blocker on the PR's ticket, or an unresolved review thread (outdated or not, whoever opened it; the output lists each thread's author and url), is a refusal (exit 1) that names the clause; a behind branch is updated (exit 5) and the PR's own change since the approved head (what it adds to the default branch, so merges of the default branch count for nothing) that touches a risk path or exceeds the S thresholds needs re-review (exit 6). The orchestrator passes `--also-approved <pr>=<sha>` for every other approved PR waiting its turn; once the merge lands, the script updates each of those that is behind (unless it is DIRTY, or pushed to since its approval; a merge of the default branch into it is not a push), so their CI runs at the same time instead of one after another. A PR whose changed files match a config **Merge gates** glob (read from the main checkout's config, so a PR can't edit the gate that judges it) is always refused, with or without `--approved-head`: `next: ask-user gate <glob>` (exit 1), and a `merge` event with outcome `gate-hold` in the run log. There is no go-ahead a script can read, since every agent runs `gh` as you: you merge a gated PR by hand (web UI or `! gh pr merge`), and the next `merge` call finds it merged and only cleans up. The sweep and `--also-approved` leave a gated PR alone. The orchestrator holds no merge-rule clause list of its own; `Orchestrator merges: no` stays its decision, as it is yours.

- **Verdict line** (ADR-0014; `common.verdict` and `common.VERDICT_WORDS` are the one implementation and the one word list): an orchestrator-facing script ends its output with exactly one `next: <word> [<args>]` line, and the run skill applies it word for word. A script that touched other PRs first prints one `also: <word> <args>` line per PR. Exit codes keep their numbers (tests and the guard read them); a new meaning gets a new word, not a new code. A rate limit is the one word `retry-after <time>` in a script that ends with a `next:` line (exit 2). A program error is `could-not-run`, never a decision. The words, by script:
  - `gate`: `review <head>` (exit 0) · `send-back <pr>` (1) · `rerun-after-ci` (3: mergeability still UNKNOWN) · `wait-older <pr> <older>` (3: the PR shares a path with an older open PR and waits for it to merge) · `wait-ticket <pr> <ticket>` (3: the only overlap is with a ticket still building or in another session, so the PR is fine; run the gate again when that ticket opens its PR or merges, whichever comes first) · `retry-after <time>` (2) · `could-not-run` (2).
  - `merge`: `frontier` (0, 4: a merge landed, so the run runs the frontier and fills the freed slot in the same turn) · `wait-ci <pr> <head>` (5, or a refusal while CI is pending; `<head>` is `?` when the head had not moved after three reads, and a rerun within 120 s of that update-branch answers `wait-ci <pr> ?` without a second one) · `re-review <pr>` (6) · `send-back <pr>` (1: red CI, unresolved review threads or a failed branch update) · `ask-user <why>` (1: an open blocker or a refused merge; only ever a real decision) · `cleaned <pr>` (0: the PR was found closed unmerged and its scratch trees removed) · `retry` (3) · `retry-after <time>` (2) · `could-not-run [<Class>: <message>]` (2; an exception is this, with the traceback on stderr). `send-back` goes to the PR's worker, to the lead for a lead PR, to the orchestrator for the chore PR; the lines above the `next:` line are what its owner gets. Before `merge`'s `next:` line comes one `also: <word> <pr> ...` line per other PR the run touched (`--also-approved`, the sweep): `wait-ci <pr> <head>`, `send-back <pr>` or `left <pr> <why>`.
  - `watch-ci <pr> [<head>]...` (a head pins the PR until its head is that commit) has no primary PR: it prints one `also:` line per PR as it settles, with the full head, and ends `next: settled`. The `also:` words: `ci-pass <pr> <head>` · `ci-fail <pr> <head>` · `no-run <pr> <head>` (a ready PR whose head has workflow files showed no check, or only skipped ones, for 5 minutes: close and reopen the PR once) · `stuck <pr> <run id> <job id>` (a finished job hangs in_progress: rerun that job; the watch carries on) · `head-not-reached <pr> <sha>` (the pinned head was not reached in 5 minutes) · `gave-up <pr> <why>` (`gh` kept failing, the PR is missing from `gh`'s list, or a pass was withheld after an earlier error in the run). Exit 3 when an `also:` line is an error kind (`no-run`, `head-not-reached`, `gave-up`). Its `next:` is `settled` (0, 3) · `retry-after <time>` (2) · `could-not-run` (2). `watch-ci` is read-only: it names a rerun and never performs one; `ci-rerun <pr>` (a `no-run`: close and reopen the PR) and `ci-rerun <pr> --job <run id> <job id>` (a `stuck` job) do it, once per head or job, print `next: rerun <pr> <head>` and log a `ci` event with outcome `rerun`; `next: already-running <pr>` (the head has a check) and `next: ask-user <why>` (already rerun once) are exit 1. Every CI wait is a `watch-ci` Monitor; the orchestrator never runs `sleep` or polls `gh api` by hand, and no budget or rate-limit rule suspends it (its tick is one REST request per PR and no GraphQL). `ci-times` flags the drift: its `wait: over` line means the median gap from CI done to merged exceeded 2 minutes; the gap includes review, approval and merge-gate time, so read it as a trend to watch, not proof of a sleep.
  - `frontier`, `snapshot`, `lead-route`, `threads` and `rescue` print their own lines first and end with the one `next:` line. `frontier`, `snapshot` and `lead-route`: `done` (0) · `retry-after <time>` (2) · `could-not-run [<Class>: <message>]` (2); `lead-route`'s `counted: <k> of <cap>` is the last line before it, and `snapshot`'s one line is the path it wrote. `threads`: `done` (0; `threads <pr> followup` prints the ticket number on the line before it) · `refused <why>` (1: nothing changed, a thread id the PR doesn't have, a resolved or open thread, a `--fixed` sha off the branch, or nothing to carry) · `retry-after <time>` (2) · `could-not-run` (2). `rescue`: `done` (0: saved, or nothing to rescue) · `ask-user overlap` (1: saved, but the paths overlap something held or the check could not run, so dispatch no worker) · `elsewhere` (3: a live lock from another session) · `retry-after <time>` (2) · `could-not-run [<Class>: <message>]` (2).
  - `holds` and `claims` keep their own line shapes (a line per held path or per claimed ticket) and end with the one `next:` line: `done` (0; `holds` also on 1, an overlap, and 3, a wait for an older PR: the lines above it are the answer) · `retry-after <time>` (2) · `could-not-run [<Class>: <message>]` (2).
  - `worker-report`: the classification is the `next:` line, applied word for word: `valid pr-opened <pr> <head>` · `valid stopped <stop-reason>` (`valid stopped transient exhausted` on the third in a row) · `interim` · `not-a-stop` · `not-a-pr-opened` · `duplicate <verdict>` · `missing-report pr <pr> <head>` · `missing-report none` · `limit [<reset time>]` · `error <gist>` (all exit 0); with `--reviewer`, `valid` or `incomplete <why>` (`--post-risk-notes` prints its `risk-notes <word>` line before the `next:` line) · `retry-after <time>` (2) · `could-not-run [<Class>: <message>]` (2).
  - `board`: `done` (0: synced, or no board) · `retry-after <time>` (1 or 2: a rate limit it gave up on) · `could-not-run [<why>]` (1 or 2: the sync did not finish, so the board's drift stays; the run carries on, the board never fails a pass). `profile.py record`: `recorded` (0) · `retry-after <time>` (2) · `could-not-run [<Class>: <message>]` (2); `profile.py <session>` and `compare` are reports, not orchestrator steps, and print none.
  - `--help` (argparse's usage output, exit 0) is the one exemption, the same for every script: it prints no `next:` line, because no orchestrator step reads it, and no CLI test covers it (#717).
  - `sweep` (the lead's breakage sweep): one `<check>: <detail>` line per finding (`red-main`, `stale-claim`, `orphan-worktree`, `new-prompt`, `failed-rescue`, `rounds`), then `clean` (0) or `findings <n>` (0); `failed-rescue` is read from the `rescue` run-log events (`rescue` appends one per run once it knows the ticket: `ok` or `failed` with the reason; the newest per ticket counts, so a failure saved by hand stays reported until a rescue `ok`), and a stalled claim is only ever a `stale-claim`; the first sweep (no `ran` event yet) is the `new-prompt` baseline: it records the kinds and prints one `note:` line, and a kind's command word is the program the command runs (`cd <dir> &&`, `(`, env assignments and `timeout <n>` stripped); `sweep --due` reads only and answers `due <n>` or `not-due <n>` by counting `merge` events since the last `sweep` `ran` event in the run log (10 merges, `ROUND_LIMIT` 3: constants in the script). A run writes that `ran` event and one `prompt-kind` event per new `<role> <tool> <command word>` kind from `prompts --all` (every prompt, whatever the digest mark), so both survive a restart. `fold <from> <into>`: `folded <from> <into>` (0) or `ask-user <why>` (1, nothing written: a ticket claimed, closed or last edited by an untrusted author, or one gated and one not by the config's Risk paths). Neither has a guard row yet, so a call prompts (#661).

After the cleanup, `scripts/merge` sweeps the other open PRs: each whose branch now conflicts with the default branch is updated and pushed to by the script itself (the orchestrator, not a worker, so the worker rule above doesn't apply). Under squash or merge it merges main into the branch with a plain push; under rebase it rebases and pushes with `--force-with-lease`. Conflicts in the files the config's **Shared files** bullet lists are resolved by replaying the PR's lines onto main (a word-level 3-way merge for a line changed on both sides); a conflicting file matching a glob under **Generated:** (nested bullets of the form `` - `glob`: `command` ``) takes main's side and the command is run in the sweep worktree against the PR's sources, its output committed; anything else, a failing or hanging command, a command that changes a file outside the generated globs, or overlapping words, is handed back: the branch is left untouched, the script prints `HANDBACK PR #n <branch>: <path> (<why>)` lines and exits 4, and the run skill resumes the worker with them. That sweep may rebase under the rebase method, but a worker never does: resumed with a conflict list, it always merges the default branch and pushes without force (`agents/worker.md`, Follow-ups). Each file's outcome (`line-replay`, `word-merge`, `regenerated`, `handed-back`) is logged as a `replay` event. A PR that is merely behind is not touched.

**Routine steps are approved, not just allowed.** A plugin can't ship permission rules, and auto mode's classifier has refused a worker's plain steps (#358), so for a call its rules accept that is one of the role's routine writes the guard answers an explicit `allow` (reason `orchestrate guard: routine <role> step`), which skips the prompt and the classifier. For a worker: `git add` and `git commit` inside its worktree, `git push` of the branch checked out in its worktree (never the default branch), `gh pr create --draft`, `gh pr ready`, `gh pr edit` and `scripts/threads [resolve]`, each only in the current-branch form with no PR number and only from inside the worker's own worktree (the PR writes and the threads calls are not approved from anywhere else), since `gh` and the script resolve the PR from the checked-out branch and a call naming a number is left to the permission layer; for a reviewer, the review post in the accepted shape when the config says `Post reviews: yes`; for the orchestrator and the lead (the main session, in a repo with `.claude/orchestration.md`), a plugin-script call that matches a row of the guard's one `ORCHESTRATOR_FORMS` table (#545), and `gh issue edit|comment|create|close`. A row names the script, its positional words in order and every flag it may carry, spelled in full with the kind of value each takes (`--repo` only `.`, `--snapshot` and `snapshot --out` only `.claude/orchestrate-snapshot.json`, gate's `--cwd` only a worktree under `<repo>/.claude/worktrees/`, scratch's `--under` only this session's scratchpad or `~/.claude/jobs/<session>/tmp`); every such script sets `allow_abbrev=False`, and `tests/test_invocation.py` checks each row against the script's `--help`. The rows: `merge <pr> [--method|--approved-head|--ticket|--also-approved|--worktree|--timeout|--interval ...]` and `merge --fast-forward-only`; `threads <pr> [--all]`, `threads <pr> resolve <id>... --fixed <sha>` or `--left <why> (--followup <n> | --no-followup)`, and `threads <pr> followup [<id>...] [--gist <text>]`; `board`; `ci-rerun <pr> [--job <run> <job>]`; `scratch <pr> <head> --under <dir>`; `worker-report <ticket> --branch <b>` and `worker-report <pr> --reviewer [--post-risk-notes]`; `issue <n>`; the read-only pass scripts `snapshot`, `rebuild-state`, `claims`, `frontier`, `holds`, `gate`, `ci-times`, `watch-ci`, `lead-route`, `lead-brief` and `prompts` with the flags the run and lead skills pass; and `python3 -I <plugin>/scripts/profile.py record ...` / `profile.py <session> --repo .`. `launch`, `sandbox-git`, `rescue` and `verify` have no row. A script word is the plugin's own file (never an env prefix or wrapper); an argument may be `$ME`/`${CLAUDE_SKILL_DIR}` when the guard knows its value, and `ME=<this session's id>` is the one extra assignment approved (the run skill writes the id out instead). `tests/test_skill_forms.py` extracts every script call from `skills/run/SKILL.md` and `skills/lead/SKILL.md` and asserts the guard approves it, so the skills and the table cannot drift. `scripts/issue <n> --repo .` is a read approved for every role. Beyond those single commands the guard approves read-only chains, a worker's test runs and edits, and a reviewer's scratch-checkout suite run (see the table above, #562). Otherwise only a single plain command is approved: a chain with any other step, an expansion, an unquoted glob, brace or tilde word (`*`, `?`, `[`, `{a,b}`, `~`, `$`) or a heredoc is left to the permission layer, so a worker runs each write as its own call. The orchestrator's `scripts/merge` is approved only as `<pr>` plus `--method`, `--approved-head`, `--ticket`, `--also-approved`, `--worktree`, `--timeout` and `--interval` (each in full, with a value; no `--cwd`), and `scripts/board` only with `--dry-run` and `--verbose`, optionally after exactly `--repo .`. A worker's `--body-file`, `--body-file=<path>` or `-F <path>` is approved only for `-` (stdin) or a path that resolves, symlinks followed, inside its own worktree or this session's scratchpad (matched on the hook input's `session_id`); the attached forms `-F/path` and `-F=path` are checked the same way, a cluster holding an `F`, spaced or attached (`-dF x`, `-dF/path`), is refused, and a scratchpad path is never approved when the hook input has no `session_id` (a worker can't write there since #567, so the forms to use are `--body-file -` with a quoted heredoc, or a file inside its worktree); any other path is refused for a worker with a reason.  A worker's file edits are approved inside its own worktree (a `.claude/worktrees/agent-*` directory) and **denied** outside it, in the main checkout or anywhere else but a temp directory outside every checkout. Your own `deny` and `ask` rules still win over an approval.

**A worker, reviewer or scout never gets the permission prompt (#567).** They run in the background with nobody to answer it, so a call no rule approves is denied with a reason that names the approved way, and a call the agent truly needs becomes a stop it reports. The reasons: a heredoc, `python3 -c`, `perl -i` or similar edit is "edit files with Edit/Write"; a write chained with reads is "run the write on its own"; a `Monitor` is "run the tests in the foreground, or wait with an approved loop"; anything else is "not approved for a worker: find an approved form, or stop and report what you need". A worker's Edit or Write outside its worktree (a temp dir included) is denied with "write scratch files inside your worktree, or pass a PR body with `--body-file -`" (a `gh pr create|edit --body-file -` with a quoted heredoc is approved). The guard failing is still a deny (ADR-0002). The lead's session, and any session you start by hand, keeps the prompt for what the guard doesn't approve.

**The orchestrator never gets the prompt either (#579).** `scripts/launch` sets `ORCHESTRATE_ROLE=orchestrator` in the environment of the orchestrator's line (plain, `--bg`, `--resume`, `--resume-latest`; the printed line carries it as a prefix) and in the `env` of the `--settings` JSON it passes, because `claude --bg` hands the session to a pre-spawned daemon that never sees the line's own environment (#628); neither is ever on the `--lead` line; the guard reads the variable, since the orchestrator and the lead are both the main session with no `agent_type`. With it set, a Bash or Monitor call the guard can't approve is denied with `not approved for the orchestrator: ...` and the approved way: a script call with a trailing filter the chain form refuses is "run the script on its own; its output is already bounded"; a hand-run `gh` or `git` form a script covers names the script (`scripts/merge`, `scripts/watch-ci`, `scripts/threads`); a call of the checkout's copy of a plugin script (`<repo>/scripts/<name>`, or a bare `scripts/<name>`) is "call the plugin's copy: `<plugin>/scripts/<name>`" (the same reason a worker, reviewer or scout gets); anything else is "use a `scripts/` entry point, or raise a `needs-lead` stop naming the command". A guard error is still a deny. Without the variable nothing changes.

**Recursive reads that follow symlinks are not approved (#586, #579).** The read bound checks the directory argument's resolved path, not what lies under it, so `grep -R`/`-S`/`--dereference-recursive`, `rg -L`/`--follow`, `find -L`/`-follow`, `ls -L`/`--dereference` and `diff -r` (without `--no-dereference`) are refused with the safe form in the reason; `grep -r`, `ls -R` and `find` without `-L` don't follow a symlink met while walking and stay approved. Also approved for a reviewer and scout: `threads <pr>` and `threads <pr> --all` (the plugin's copy, nothing chained); and `git -C <dir> <read>` when `<dir>` is inside the read bound and the subcommand is one already approved.

Also approved (#567), within the read bound of #566: a worker's `git switch -c <n>-<slug> origin/<default>` or `git switch -C <n>-<slug> origin/<that branch>` (alone or as one segment of a compound); relative globs in read arguments (expanded, every match held to the bound); `until|while <read-only test>; do sleep N; done` waits (`pgrep`, `test -e <allowed path>`), for `Bash` and `Monitor` (the matcher is `Bash|Monitor`; the orchestrator's `watch-ci <pr> <sha>` Monitor is a plugin-script call); a plain `NAME=word` variable followed by reads that use it; a reviewer's `<plugin>/scripts/scratch <pr> <head> --under <its scratchpad>` (a hand `git worktree add` is refused for every role: the script is the one way to add a scratch worktree, #545); the orchestrator's chains whose every segment is approved, `cat <<'EOF' | worker-report ...`, `S="$PWD/scripts"` and `scripts/prompts`. Refused: a long option of a read command that isn't spelled in full (`grep --fil`), `git diff --no-index` or any git read verb on a path outside the bound, and `git ls-remote` of anything but `origin`; `git remote add|set-url` is approved for no role.

A running session loads `hooks/hooks.json` once, so a new entry (the `Monitor` matcher, the prompt log) takes effect only after the session restarts; edits to `guard.py` apply on the next call.

It splits the command into shell words (quotes, escapes, `$(...)`, heredocs, `sh -c`), decides on those, and refuses a command it can't parse. It's a guardrail against mistakes, not a sandbox. Your permission mode and sandbox settings still apply on top.

## The prompt log

`hooks/prompt_log.py` runs on Claude Code's `PermissionRequest` event, which fires right before a permission prompt shows, for the orchestrator and for every worker, reviewer and scout. It appends one JSON line to `.claude/orchestrate-prompts.jsonl` in the main checkout (a worktree's prompts land there too) and decides nothing: it prints nothing and exits 0, even on a malformed payload or an unwritable file (one line on stderr), so the prompt still shows and your choice is unchanged. Each line holds `time`, `session_id`, `agent_type` (null for the orchestrator's own session), `tool_name`, `cwd`, `permission_mode` and a cut-down `tool_input`: a Bash or Monitor `command` cut to 2000 characters, the `file_path` of an edit or a Read, the `path` (null when absent) and key names of a Grep or Glob, and for any other tool (Skill, MCP) the key names only. No file contents, no search pattern and no other arguments are stored. The file is local and gitignored.

The file holds commands of up to 2000 characters in clear text, so it is created with mode 0600 (an existing 0644 file is chmod-ed on the next write).

`PermissionRequest` does not see every prompt (#579): the "Claude requested permissions to edit <path> which is a sensitive file" prompt comes from a path-safety check that returns before the hook path. So the same script is also registered on the `Notification` event, matcher `permission_prompt|worker_permission_prompt`, the two notification types Claude Code sends when it shows a prompt. Each line has `"source"`: `request` (PermissionRequest, with `tool_name` and `tool_input` as above) or `notification` (no tool: `message`, `title` and `notification_type`, each cut to 500 characters). `scripts/prompts` counts a prompt once: a notification line within 2 seconds of a request line of the same session is the same prompt; an unpaired notification is counted on its own, with the tool `?` and its message. A prompt that fires neither event is not logged and not counted: for those, read the session with `claude logs <session>`. (Which events each prompt type fires, with payload fields, is recorded in the PR that added the notification hook, #579.)

`scripts/prompts --repo . [--session <id>] [--since <iso> | --watermark]` counts the prompts by role and tool and lists the newest 40, one line each. The roles (#642): a subagent's own type (`worker`, `reviewer`, `scout`); `orchestrator` for a line whose `role` field is `orchestrator` (the hook writes `role` from `ORCHESTRATE_ROLE`, which `scripts/launch` sets on the orchestrator's line only, and writes no field when the variable is unset); `lead` for a main-session line whose session is named `lead` in `claude agents --json --all`; `main` for any other main session (a hand-started one, or one the lookup cannot name). A line logged before the `role` field falls to the name lookup, then `main`, so an old log never fails to count. `--watermark` means since the last mark: the newer of the last `--mark` (a line in `.claude/orchestrate-prompts.mark`, written with or without `--profile`) and the last pass record. With neither yet it counts the whole log and says so on the `prompts:` line. The run skill's pass table and the lead's pass digest take their **Approvals** lines from it (the digest also names any new kind of prompt, to be filed or folded like a breakage), so the count is exact (0 shows as 0) and does not depend on anyone's memory.

## Push and fetch under the sandbox

On macOS, `git fetch`, `pull` and `push` over an SSH remote fail inside the sandbox even when the host is allowed, because plain ssh ignores the sandbox proxy ([docs](https://code.claude.com/docs/en/sandboxing)); agents see `Permission denied (publickey)`. On Linux and WSL2, git's SSH is tunnelled through the sandbox proxy once the host is in `sandbox.network.allowedDomains`, so that alone is enough. For an SSH remote, `/orchestrate:setup` offers, with your yes, to run `scripts/sandbox-git`, which adds `git fetch *`, `git pull *` and `git push *` to `sandbox.excludedCommands` and the remote's host to `sandbox.network.allowedDomains` in `.claude/settings.local.json` (gitignored; leave it uncommitted; nothing under `~/.claude` is touched). Those three git commands then run **unsandboxed** and can reach any host. `excludedCommands` matches the command text, so a command run from inside a script or wrapper isn't matched, and workers push with plain `git push` ([docs](https://code.claude.com/docs/en/sandboxing)). Without that, a worker pushes over HTTPS through `gh`'s credential helper for one call (`git -c credential.helper='!gh auth git-credential' push https://github.com/<owner>/<repo>.git <branch>`), which needs github.com reachable from the sandbox. A worker never turns the sandbox off to push.

## CI on draft PRs

Every worker opens a draft PR at the end of Orient and pushes to it while it builds, so a workflow that runs on drafts spends a CI run per push that nothing reads until `gh pr ready`. `/orchestrate:setup` runs `scripts/setup-check --repo .`, which flags each `.github/workflows/*.yml|yaml` that has a `pull_request` trigger and mentions neither `draft` nor `ready_for_review` (a text scan outside comments; push-only workflows are ignored and it does not judge which jobs run tests), prints `flag <path>` per hit and ends with `next: advise` or `next: none`. For each flagged file setup shows a suggested diff: `types: [opened, synchronize, reopened, ready_for_review]` under `pull_request:` and `if: github.event_name != 'pull_request' || github.event.pull_request.draft == false` on the jobs, the change this repo's `ci.yml` carries (#666). Setup never writes the workflow and never opens a PR for it (ADR-0013). A repo that takes the advice relies on an all-skipped check rollup reading as pending, not as a pass, in `watch-ci` and `merge` (#729).

## Measuring CI wait

`scripts/ci-times [--since <time or PR>]` tells you whether CI wait is over the limit and whether the cause looks like too few runners or one slow job. It reads merged PRs only, works with lead mode off, and prints the median and p90 push-to-green, the slowest checks with queued and running time, and `over: yes|no`.

- **Push-to-green** runs from a head's commit time (not the push time, which `gh` does not give per commit, so a late push or a rebase skews it) to its last check going green. Heads that never went green are left out; a fix push counts as its own head.
- **Window:** the last 10 merged PRs, or every merged PR since a time or PR with `--since`.
- **Limit:** over means a p90 above 10 minutes. Set `- **CI wait limit:** <minutes>` in the config's Review section to change it.
- **Cause:** a hint, not a diagnosis. When over, `runners` if the slowest check (by median) waited longer than it ran, else `slow job`. Queued is measured from the commit, so a job that `needs:` another shows the upstream job's runtime as queued and can read as `runners`.

## Running out of usage

Every agent draws on your plan, so a usage limit tends to stop several workers at once.

- The first usage-limit error in a pass stops all new dispatches. The affected tickets show as **paused**, with the reset time when the error gives one.
- The next pass after the reset continues each paused worker where it stopped, with its context. A worker it can't reach (another session) is replaced by a new one on the same branch; first the orchestrator commits and pushes any work left in the old worktree as `chore(wip): …`. `scripts/rescue <n>` finds that worktree by the worker's agent id, as `scripts/claims` does, so a worker paused before Orient's branch step (its worktree still on `worktree-agent-<id>`) is rescued too: rescue creates the ticket branch from the worktree's HEAD and pushes it. If the overlap check stays rate-limited past the wait budget, rescue still exits 0 and prints `overlap: unchecked`, to be re-checked with `holds` before dispatching.
- Workers push after every commit whose checks pass, so little is lost.
- `.claude/orchestrate-state.json` (gitignored) remembers each ticket's worker, worktree, model and last report between passes. `scripts/rebuild-state` rebuilds it from the session's transcripts at the start of each pass, joining workers to tickets by the `#<ticket>` in their dispatch description (`Build #<ticket>`); the orchestrator never writes it. A worker's worktree is the one its completion notice reports (on a branch `worktree-agent-<id>`), else its agent's directory under the harness's worktrees, else the checkout of its ticket's branch; the file records the first that exists, with the touch map the brief names. The file keeps one entry per session (`{"session": <the session that rebuilt last>, "sessions": {<id>: {"tickets": ...}}}`); a rebuild replaces only its own session's entry, under an exclusive lock on `orchestrate-state.json.lock`, and writes a temp file it renames over the state file, so readers take no lock. The scripts read the current session's entry as Building; a record under another session's id is a candidate for Elsewhere (when its worktree's lock is live), never Building. By default the current session is the one that rebuilt last; `claims`, `lead-route`, `holds` and `gate` take `--session <id>` (and `rebuild-state` takes it in place of its positional id), and with it "current" is that id, so two live sessions on one checkout never read each other's records as their own (`rescue` and `board` don't take it yet and still follow the last rebuild). Each rebuild also drops the entries of sessions that are not a row of `claude agents --json --all` (live or stopped); if `claude` is missing or its answer is unreadable, nothing is dropped. A file in the old `{"session", "tickets"}` shape is read as one session and rewritten in the new shape on the next rebuild. The tracker stays the source of truth.

While a limit holds and the orchestrator can still run, it schedules a one-shot cron at the reset time, in hops of at most 60 minutes; each hop runs a `status` pass. These cron jobs are session-only and fire only while the REPL is idle.

For unattended runs, turn on **Continue automatically at usage limit** in `/config` (`autoContinueAtUsageLimit`). Without it, a session whose own turn hits the limit ends after one retry about 20 minutes later; run `/orchestrate:run` again and the pass picks up where things stopped. A fallback model doesn't help: rate-limit errors never trigger one, and the orchestrator never switches models on its own.

## Lead mode

A lead session can sit above the orchestrator to answer its questions and triage discovered work ([ADR-0008](adr/0008-lead-above-orchestrator.md)). Lead mode is detected, never configured: a live session named `lead` turns it on, and every pass report starts with `Lead: live` or `Lead: none`.

- **What it does and doesn't.** The lead answers stops and ADR conflicts, triages discovered work and records settled decisions through its own PRs (the ADR and glossary terms, behind a ticket it filed). It never builds, reads diffs, opens or reviews PRs, merges anything ([ADR-0004](adr/0004-merge-sweep-belongs-to-the-orchestrator.md)) or dispatches workers; the orchestrator does all of that.
- **Names.** Start the orchestrator session and name it `orchestrator` (`/rename orchestrator`); `/orchestrate:run` asks once if the name is wrong, and stops if another live session already has it. Name the lead `lead`.
- **Stops.** With a live lead, a worker's question on an ambiguity goes to the lead: the ticket gets `needs-lead`, keeps its claim and its slot, and a stop comment starting with `> *Stopped for the lead.*` carries the question. The lead answers on the ticket and removes `needs-lead`; the next pass resumes the worker with a pointer to the answer. Without a lead, the stop goes to you as before (`needs-info`).
- **Routing.** `scripts/lead-route` prints each pass's routing decisions from the tracker and the state file, and prints no tracker writes. Its first line is `lead: live` or `lead: none`: lead mode is the one live session named `lead` whose `cwd` is this repo's main checkout (so another repo's lead, or a `lead` in a worktree, never gets this repo's stops); a failed or ambiguous lookup is `lead: none` for that pass, with the reason on stderr. After 30 minutes with no answer, a `needs-lead` ticket stops counting against the slot cap while its worker waits. If the lead goes away, a `needs-lead` ticket falls back to `needs-info` and you get it back.
- **Split, narrowed and dropped tickets.** If the lead splits a claimed ticket so that it has an open blocker, the orchestrator hands it back: unassigned, worker stopped, branch kept (the worktree is removed only when nothing in it is uncommitted or unpushed). A narrowed or reworded ticket simply resumes its worker on the same branch. A ticket closed `wontfix` while claimed stops its worker and closes its PR unmerged, keeping the branch.
- **ADR conflicts.** A worker in lead mode reports an ADR conflict and never writes ADRs. The ticket gets `needs-lead` with a comment holding the conflict and the PR link, and the PR is held before merge while CI, gate and review still run, with no time limit. When the lead removes `needs-lead`, the PR merges. With no lead, the hold becomes a question to you in the pass report.
- **Discovered work.** The orchestrator forwards each `discovered:` line from a worker or reviewer report to the lead, with the PR URL and gists, and creates, labels and dedupes nothing itself.
- **Lead tickets and PRs.** A ticket labelled `lead` is the lead's own work: `run` never dispatches it, and it holds no slot. Once the lead opens the PR that closes it, that PR goes through the same pipeline as any other: CI, gate, review and merge, merged by the orchestrator. A failure on it (CI, gate, review or a hand-back) goes to the lead. If the lead can't be reached, the ticket shows as waiting on the lead (not delivered), and the next pass sends the failure again, once per head commit.
- **Risk notes.** An L-tier review puts its risk notes (`path:line-range — what to look at`) in the posted review. When the review wasn't posted, `worker-report <pr> --reviewer --post-risk-notes` (the script that parses the reviewer's report) posts them as one PR comment starting `> *Risk notes (review not posted).*`, once (a trusted author's comment with that first line is never followed by a second), lead mode or not; with no lead, the end-of-run summary lists them too.
- **Start-up index.** `scripts/lead-brief` prints, in one call and in fixed order: the config, the tracker docs, the full glossary, an ADR index, open `needs-lead` then `lead` tickets, the roadmap (open `wayfinder:map` issues and open parents, with sub-issue counts) and the PRs merged since the watermark, each L-tier merge followed by its risk notes word for word. A section it can't read prints `unavailable: <why>` and the rest still prints. `--checkpoint <pr>` writes the watermark (`.claude/orchestrate-lead.json`, written by this script only), so a new or compacted lead resumes there; with no readable watermark it shows the last 7 days of merges, at most 20, and says so.
- **Starting the lead.** `scripts/launch --lead` starts the whole system (the lead runs on the **Lead** row of the config's Models table, Opus by default, passed as `--model`; with the row missing or blank it gets the account default, and a hand-started `/orchestrate:lead` keeps its own model; `/model fable` suits its charting and grilling, which it says once at that step; `scripts/launch --lead --print` shows the line, which accepts `crossSessionInbound` so a bypass orchestrator's messages reach the lead without a click). The lead checks its own name (asking once to `/rename lead`, stopping if another live session has it), reads the config and tracker docs, runs `scripts/lead-brief`, then checks `claude agents --json --all` so it never starts a second orchestrator: a live `orchestrator` row is reached by `SendMessage`, a `pid: null` row is resumed (with several stopped rows and none live, `scripts/launch --resume-latest --bg` picks the one of this repo with the newest `startedAt` and prints which it chose), and with no row it runs `scripts/launch --bg`. The lead takes `--greedy[=N]` or a ticket, and `--profile` (`scripts/launch --lead --greedy=4 --profile`); it passes them to `scripts/launch --bg` when it launches a fresh orchestrator, and says so in one line when a live or stopped orchestrator keeps its launch flags instead. `scripts/launch` owns the line (see "Starting the orchestrator" under Use it in a repo): the model comes from the config's Orchestrator row, so with it missing, blank or old-style the orchestrator gets the account default and the lead says which. A first-turn `model_not_found` failure gets one relaunch with `--no-model`; a usage limit never does.
- **Two terminals.** Start the orchestrator yourself in one terminal with `scripts/launch`, then `scripts/launch --lead` in another. The lead finds the live `orchestrator` row and launches nothing. Either order works.
- **Pass reports and the watch.** With a lead live, the orchestrator sends the lead each pass report (the table, the Approvals lines and every item below it) and the asks that would otherwise stay in its terminal: parents to close, `ready-for-human:` and `drift:` lines, and the URL of every ticket it filed. A held or refused delivery is one line in the report and doesn't fail the pass. The lead also watches the tracker itself: at start-up it runs `scripts/lead-brief --watch` in the background, which exits on a new issue, a new `needs-lead` ticket a takeable ticket whose body `Blocked by:` line names only closed issues, or an idle slot (`idle-slot:`, see [Keeping slots full](#keeping-slots-full)) (reading the tracker at most every 5 minutes, never writing to it, ending with a `next:` line). The lead triages or grooms what it named, then starts the watch again, and scans the backlog for folds on every pass digest.
- **Questions for you.** With a lead live, the orchestrator never asks you directly: every ask goes to the lead, which answers it or bubbles it up to you with its recommendation. The lead answers judgment calls inside the build loop (a third review round, closing a parent whose children have all merged, a slot suggestion, a hand-back or abandon, which of two in-flight PRs goes first). It relays what the config or repo reserves for a human (config gates, Human-only steps, release PRs, repo settings, permissions, spending money) and anything it is unsure of, and never answers a relayed ask for you. Two asks always reach you directly: a permission-denied stop, and a merge gate on a PR that changes the permission layer itself (`hooks/**`, `.claude-plugin/**`, the guard). If the lead can't be reached, the orchestrator asks you itself.
- **Without a lead.** Every part falls back to you, and dispatch, review and merge run as before. A stop becomes `needs-info`, answered on the ticket. An ADR conflict holds its PR before merge and becomes a question in the pass report. Discovered work appears as PR URLs in the pass report, and L-tier risk notes go into the end-of-run summary. Each pass report says `Lead: none`.

```
scripts/lead-route --cap <n> [--repo .] [--state FILE] [--snapshot FILE] [--now ISO]
scripts/lead-brief [--repo .] [--now ISO] [--checkpoint <pr>] [--watch [--interval SECONDS]]
```

`lead-route` is run by the orchestrator each pass, `lead-brief` by the lead at start-up and after a compaction. Their `--now` is for tests.

## Running on a public repo

On a public repo anyone can comment on a ticket or open a pull request from a fork, so orchestrate acts only on text from a **trusted author**: `author_association` `OWNER`, `MEMBER` or `COLLABORATOR`, or a login on the config's optional `- **Trusted authors:** `login`, `login`` line (Backlog section). A login matches exactly, so list a bot with its suffix (`dependabot[bot]`); `dependabot` trusts only the user of that name. Comments from anyone else are counted and never read:

- A worker and a reviewer read the ticket body and a trusted author's comments (the tracker doc's **Read an issue** filters them). A stranger's `## Agent Brief` is not the spec. The body is trusted once a collaborator has applied `ready-for-agent`, since only collaborators can label.
- `lead-route` and `lead-brief` parse stop, ADR-hold and resend markers, risk notes, `tier:` and discovered work from trusted comments and reviews only.
- A **fork PR** (its head is in another repository) is never a ticket's PR: it holds no path in `holds`, is no claim, no board card and no worker-report match. `merge` never acts on one.
- A worker addresses review threads from trusted authors only. `threads` lists an untrusted thread as `untrusted (text withheld)` and refuses to resolve it. It still blocks `merge`, which names it as untrusted and asks you to resolve or dismiss it: an outsider can stall a merge, never cause one.

To hear an outside voice, restate it in your own comment or add the login to `Trusted authors:`. GitHub settings that help: under Settings > Moderation options, interaction limits (restrict comments to prior contributors or collaborators); under Settings > Actions > General, require approval for workflows from fork pull requests. The rule is in `docs/adr/0015-act-only-on-trusted-tracker-text.md`.

## Projects board

Setup offers an opt-in GitHub Projects board. It needs the token's `project` scope (setup gives you `! gh auth refresh -h <host> -s project` to run (`<host>` is the host of `origin`, `github.com` for a github.com remote), and offers retry or skip), creates the project under the repo owner and links it to the repo (falling back to your own account, unlinked), and writes `- **Board:** <project URL>` into the config itself. With that line, `/orchestrate:run` runs `scripts/board` in step 5 of every pass; without it the script does nothing.

The board is rebuilt from tracker, PR and claim state only (the claim states are `scripts/claims`'s, so the board never decides a claim itself), in the single-select field `Stage` (created on first sync; GitHub's built-in `Status` options can't be edited through `gh`). The columns run left to right as a ticket's life: **Backlog** (open, unclaimed `ready-for-agent` tickets that are not parents and carry no `wayfinder:` or `lead` label: the takeable ones first, in `scripts/frontier` order, then the held ones by issue number), **Building** (claimed, not in review: building, elsewhere, stalled or with the lead), **In review** (claimed, open PR), **Needs lead** (`needs-lead`; empty with lead mode off), **Waiting on you** (`ready-for-human` or `needs-info`) and **Done** (merged, archived a day later). A card is added when its ticket first qualifies for Backlog or is first claimed. The lead's own `lead` tickets, which are never assigned, get a card too (from `scripts/lead-route`'s `LEAD-TICKET` and `LEAD-PR` lines): Building with no PR or a draft, In review with a ready PR. A Backlog card whose ticket stops qualifying without being claimed (relabelled, closed) is deleted; one that gets claimed moves to its stage. Sync orders the Backlog cards with GitHub's `updateProjectV2ItemPosition` mutation, only where a card is out of place. A board made before Backlog existed is upgraded in place: sync adds the missing option and puts the options in column order with `updateProjectV2Field`, keeping every existing option's id and color. The tracker is read once per sync. A card whose ticket closed without a merged PR (a `lead` ticket, say) is archived, since a card's life ends with its ticket. The board only touches cards whose content is an issue of this repository, keyed by repository and number: draft cards, hand-placed cards and other repositories' cards are never moved, archived or deleted. If `lead-route` fails, the lead's cards are skipped for that sync with one stderr line and the rest still syncs. Running it twice changes nothing: sync reads the project's fields and items in one GraphQL query (one more per 100 cards) and writes only what differs from the wanted state, so a board that already matches makes no write. The writes go out as aliased mutations, at most 20 to a request, so three changed cards cost one mutation; new cards add a content-id read and a mutation for the adds first. `scripts/board --dry-run` reads everything and prints each write it would make (and each card it leaves alone), then `<n> writes planned`, without making one. `--verbose` prints `writes: <n>` on stderr (the board has no other output, so the flag only adds that line).

Switch the project's view to the **Board** layout, grouped by `Stage`, once by hand: views have no `gh` or API surface, so the script can't do it. The option order is the column order. A failure prints one line and exits 1 (2 when the owner lookup got no owner: `board: owner lookup failed: <gh message>`), and `run` carries on. The lead never reads or writes the board, and GitHub's built-in project workflows aren't used.

```
scripts/board [--repo .] [--dry-run] [--verbose]
```

## Profiling

`/orchestrate:run --profile` runs normal passes, and at the end of each one records the pass and saves a profile of the session so far. Each pass also records why free slots stayed idle (`overlap`, `gate`, `empty` for nothing takeable, `limit`), so with `--greedy` the profile shows whether a higher cap would have run more, or whether overlap and an empty backlog were what held it back:

```
Profile · session 346d1ea2 · 2026-11-03T16:01Z → 2026-11-03T16:22Z (21m) · 2 slots
proxy $ $3.09 per merged ticket (2 merged): opus $1.52 · sonnet $1.35 · haiku $0.22 · orchestrator $1.52
slots   occupied 59%  (building 37%, review/merge 22%)  idle: overlap 5m, empty 7m
plan    5h window 22% → 51%, peak 51%, 14.5 pts per merged ticket (7d 2.0) · 0 limit hits
saved   .claude/orchestrate-profiles/2026-11-03-346d1ea2.json  (+ .html)
```

- **Slot efficiency:** how much of the session's slot time held a ticket, split into building and review or waiting to merge, and why idle slots were idle (overlap, gate, nothing takeable, `unchecked` when `holds`, `frontier` or `claims` could not run, usage limit). A wake that dispatches, merges or resumes a ticket records a pass (scope `wake`), so event-driven time is attributed too.
- **Proxy $ per merged ticket:** the whole session's cost (the orchestrator and every agent, priced per request at API list, by model and token type) divided by tickets merged, split by model and by role, with a per-ticket table of worker, reviewer and other cost. The prices are a dated constant at the top of `scripts/profile.py`; they are a proxy for plan usage, not your bill.
- **Usage efficiency:** tokens by role and model (input, output, cache read, cache write), tokens per merged ticket, the orchestrator's share, cache hits.
- **Review quality floor:** from the reviewers' own transcripts, so it works with posting on or off: rounds per PR, round-1 approvals and the round-1 "changes" rate, approved-with-minors PRs that merged with no round 2, and later rounds by the same reviewer (continued) versus a new one (fresh).
- **Workers by model:** each worker's model comes from its metadata. Tickets whose workers ran Haiku and then something stronger count as escalations. Usage, requests, median and p90 context per request, tool-output tokens (estimated at 4 characters each), rounds and round-1 approvals are split by worker model; a ticket counts under the model that finished it, except round 1, which is credited to the model that started it.
- **Depth-2 agents:** any agent that a dispatched agent spawned (joined to it by `toolUseId`) is listed as a defect, and the profile warns.
- **Orchestrator turns by job:** each of the orchestrator's turns is put in one job, by the tool or plugin script it called first (`watch-ci` and Monitor are CI waits, `gate` is review posting, `rebuild-state` is the state file, `merge` is merge and cleanup, Agent is dispatch), with a few command patterns as the fallback for hand-run commands. A turn with no tool call is end-of-wake text if it says anything, else no tool call. The profile reports turns and proxy $ per job per merged ticket, so you can see which jobs left Opus.
- **Context over time:** the orchestrator's context size at each turn, plotted with its compactions (trigger and `preTokens`); the effective window (the median `preTokens` of auto compactions); hand-back tokens per role, the orchestrator's own text and Bash output (all estimated at 4 characters a token); and idle wakes, the passes that dispatched, reviewed and merged nothing.
- **Merged tickets:** counted from the merge script's `merge` events (outcome `merged`); a session with no events log falls back to merge commands in the transcript and reports those merges as unverified. Slot efficiency is measured against each pass's own slot count, and the header shows `3→2 slots` when the count changed.
- **Script events:** read from the run log's `events.jsonl` in the main checkout, beside the pass log: script-gate runs (pass, fail or unknown; failures are counted apart from review rounds, and per ticket in the table), CI runs, merges and the shared-file hand-back rate. Without the log, the viewer says so.
- **Headroom:** usage-limit hits and reset times, from transcripts and the pass log. Plan usage (5-hour and 7-day percentages over the session, 5-hour windows that reset under 50% (`--threshold`) while every slot was full and tickets waited, and points used per merged ticket, unweighted) appears only when a legacy `usage.jsonl` exists; otherwise the profile says headroom isn't measured. A profile recommends one more or one fewer slot when the history supports it; the per-pass [slot suggestion](#choosing-a-slot-count) is separate.

- **GitHub calls:** every `gh` attempt a script makes through `scripts/github.py` appends a `gh_call` event to the events log (script, method, endpoint or subcommand, GraphQL or not, status, milliseconds, and `x-ratelimit-remaining`, `x-ratelimit-used` and `retry-after` when `gh` shows them; never a body, query or token), and a sleep for a rate limit appends a `wait`. The guard also logs each `gh` command an agent runs itself, a worker's, reviewer's, scout's or the orchestrator's direct call rather than one a script makes: a row with `role` set and script `agent:<role>`. The profile totals them per pass and for the run: calls, writes, GraphQL calls, retries, calls per script, the lowest `remaining` seen, the busiest minute of writes, GraphQL points per pass (the sum of the `cost` recorded on GraphQL calls, printed as a `graphql points per pass` line when the log has costs), and the time slept (with how much of it was waiting on another script's hit, which shows whether one 60 s pause was multiplied across scripts). Read writes per minute against GitHub's secondary limits, 80 content-creating requests a minute and 500 an hour per user, and `remaining` against the hourly quota. Calls through `gh pr` and `gh issue` show no headers, so they are logged with `headers: unavailable` and no `remaining`. The summary's `GitHub calls by source` line splits the run's calls into scripts and agents, with the agent calls counted per role. A log without these events prints `GitHub calls: not recorded`. `ORCHESTRATE_GH_LOG=off` stops the logging.

Profiles live in `.claude/orchestrate-profiles/` (gitignore it). Open the `.html` beside each one, a copy of `viewer/profile.html` with the profile embedded: proxy $ per merged ticket, the orchestrator's turns by job, context per turn and script events, the review quality floor and workers by model, a slot timeline, tokens by role, plan usage over time, and tables behind each. Drop several profile JSON files on any copy to compare sessions.

**Plan headroom is not measured.** Claude Code gives plan usage only to the status line, and a plugin cannot add to or wrap the user's status line (a plugin's `settings.json` honors only `agent` and `subagentStatusLine`; checked against Claude Code 2.1.311), so the profile has no 5-hour or 7-day figures and says so. Limit hits and reset times still come from transcripts and the pass log. If you added the old `usage-tap.py` line to your status-line script, you can remove it; if `~/.claude/orchestrate/usage.jsonl` still has samples in the session, the profile reads them.

A profile prints the span it covers and warns when a transcript has records later than its end, which means it is partial (a session still running). `scripts/launch --resume` appends a `resume` event to `events.jsonl`; the profile reports each **Session gap** (from the session's last transcript entry before the event up to the event) as `metrics.session_gap` (total and intervals) and leaves it out of `span_s`, so downtime isn't counted as slow work; the viewer adds "· session gap 2h 10m, outside the span" to the subtitle and shades the gap on the timeline and plan-usage charts. A transcript silence over 30 minutes that no `resume` event explains (a hand `claude --resume` skips `launch`) is listed in `metrics.unexplained_silences` and shown as a warning banner; it stays inside the span. The JSON is `schema` 3; the viewer reads only that, and `compare` refuses a profile of any other schema or one with no pass log.

Any past session can be profiled after the fact, without `--profile`, by its ID or transcript path:

```sh
python3 -I ~/.claude/plugins/cache/claude-orchestrate/orchestrate/<version>/scripts/profile.py <session id> [--repo PATH] [--slots N] [--threshold 50]
```

Without a pass log, idle reasons and whether slots were full with work waiting show as unknown.

To judge a trial against a baseline, profile both sessions with the same version of the script, then:

```sh
python3 -I ~/.claude/plugins/cache/claude-orchestrate/orchestrate/<version>/scripts/profile.py compare <baseline.json> <trial.json> [--max-cost USD] [--max-orchestrator-cost USD]
```

It prints the headline figures side by side with deltas (merged tickets, proxy $ and orchestrator $ per merged ticket, the round-1 "changes" rate, outright and with-minors round-1 approvals, rounds per PR), the L-tier share and each tier's $ per merged ticket (a PR's tier is the one its first reviewer was dispatched at). A second table gives the gating figures as measured and again mix-adjusted: each tier's figure in the trial reweighted by the baseline's tier mix, so a trial that drew more L tickets isn't judged dearer for that alone. The orchestrator's $ isn't attributed to tiers, so it isn't adjusted. The two $ targets aren't in the script; pass them from the spec (`--max-cost`, `--max-orchestrator-cost`) or those rows go unjudged. The review-quality rows are judged against the baseline: no more "changes" or rounds per PR, and as many round-1 approvals outright or counting approve-with-minors. The trial is flagged **INCONCLUSIVE** when it has fewer than 20 merged tickets, when its L share differs from the baseline's by more than 25 points, or when the mix adjustment flips a gating verdict.

To trial the orchestrator on a backlog:

1. Run plain `/orchestrate:run` (add `--profile` if you want per-pass records) and let it work until a pass ends with nothing in flight.
2. Note the session ID, then profile the finished session by hand:

```sh
python3 -I ~/.claude/plugins/cache/claude-orchestrate/orchestrate/<version>/scripts/profile.py <session>
```

## Development

Tests: `python3 tests/run_parallel.py` (one process per test module, in parallel) (Python 3.9 or later, stdlib only).

**Behavioural tier (opt-in).** `ORCH_BEHAVIOUR=1 python3 -m unittest discover tests/behaviour` runs real headless `claude -p` agents against a temp repo with a fake `gh`, 3 runs per case (3/3 pass, 2/3 flaky, less fail), and prints a table with cost. Each run is capped at $1 and 40 turns, so a case costs at most $3; it is skipped without the variable, and CI never sets it. `ORCH_BEHAVIOUR_RUNS=1` cuts it to one run per case while you iterate. The cases (`tests/behaviour/test_*.py`) replace the phrase tests they match: the worker writes its PR body with the `:pr` skill (with and without the stub), cites a source for an external fact, and stops on a held path; the scout reports a PR one commit behind as behind; the reviewer posts one accepted review and returns its URL; and an S ticket is dispatched to a haiku worker.

**Exit codes of the scripts under `scripts/`.** One convention, so a broken environment never reads as a verdict:

- `0` ok.
- `1` a verdict: a check failed, or the action was refused (a worker is sent the output).
- `2` could not run: a missing tool (`gh`, `git`), bad input or a missing directory, or output the script could not read. Nothing about the code under test was decided; fix the environment and run it again.

A script may add its own codes above 2 for a specific state (`gate` 3 and `merge` 3/4 are documented in their docstrings). `common.run` reports a missing binary as code 127 instead of raising, and `gate`, `merge`, `watch-ci` and `verify` turn that into 2. `verify --config` (what every brief's `Verify:` line runs) reads the commands from the config's **Verify** section: each top-level bullet opening with a backticked span is one command, run exactly as written (no caller shell expands it), a bullet that is just `` `--then` `` starts a dependent group, and any other line is prose. A missing config, a missing section or one with no commands exits 2; `--config` with `CMD` arguments does too. Commands run by `verify` and `gate` get `--timeout` seconds (default 1800); one that outlives it is killed with its process group and fails with "timed out after Ns".

**How scripts under `scripts/` are found and run:** see [ADR-0003](adr/0003-script-invocation.md), checked by `tests/test_invocation.py`.

**Guard regression corpus.** `tests/fixtures/guard-corpus.jsonl` holds every distinct Bash call the plugin's subagents made in real sessions, one `{role, command, expected}` line each, and `tests/test_guard_corpus.py` runs `hooks/guard.py` over all of them, so a guard change that flips a decision shows up in the PR diff of the corpus. To add sessions (rerunnable, no duplicates, existing labels untouched), run the CLI from the repo root:

```
scripts/guard-corpus <session id or transcript path> [...] [--projects-dir ~/.claude/projects] [--dry-run]
```

It reads `<session>.jsonl` and `<session>/subagents/*.jsonl` and writes nothing under `~/.claude`. Commands are normalised before they are stored: home and repo paths, emails, token-shaped strings, heredoc bodies and long quoted text are replaced, and no tool output is kept. A line whose quoted text became `TEXT` (a `bash -c "..."`, `python3 -c "..."` or `gh api "..."` call) is a shape check, not the original command. Lines marked `"source": "hand"` are written by hand to pin refusals no session exercised. A new line's `expected` is a snapshot of the guard's decision (run in a directory whose config turns review posting on); read the new lines, especially the write-shaped ones (`git push`, PR merge, create or review, `gh api` with a method or `-f`/`-F`, `gh issue` edit, close or comment). If the guard is wrong, set the right `expected` and add `"gap": "#<ticket>"` for a ticket against the guard; the test then requires the guard to still be wrong there until the fix removes the `gap`.

## Limits

- Workers branch from the default branch (Claude Code's worktree default), so a ticket starts only after its dependencies have merged.
- Agents from a plugin ignore `permissionMode`, so workers follow your session's permission mode.
- The orchestrator stops for anything destructive or outward-facing the config doesn't authorise.
- The guard is a guardrail against mistakes, not a sandbox. Your permission mode and sandbox settings still apply on top ([the guard hook](#the-guard-hook)).
